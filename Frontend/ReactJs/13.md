# React — Context-Driven Mini App (Products, Cart & View Switching)

This module covers a larger, real-world app — an eBay-style marketplace — that uses a **single Context** as the backbone for the *entire* app's shared state: which "page" is currently showing, and the full shopping cart logic (add, update quantity, auto-remove, checkout). No router library is used at all — view switching is handled entirely through context-driven conditional rendering.

---

## 1. Architecture Overview

```
main.jsx
  └── ContextProvider   (owns: toggle, about, cart + all cart logic)
        └── App.jsx      (reads toggle/about → decides WHICH view to render)
              ├── Navbar.jsx        (writes toggle/about → switches views)
              ├── ProductCard.jsx   (reads/writes cart)
              ├── Cart.jsx          (reads/writes cart)
              └── About.jsx         (pure static content, no context)
```

Every piece of shared state — `toggle`, `about`, `cart`, and the two cart-mutating functions — lives in **one** context (`MyContext.jsx`), following the same state-lifting principle from earlier notes: since `Navbar`, `App`, `ProductCard`, and `Cart` are siblings/cousins in the tree that all need to read and/or write this data, it's lifted to the nearest shared ancestor — here, the very top of the app, via `ContextProvider`.

## 2. `MyContext.jsx` — The Central State Hub

```jsx
import { createContext, useState } from "react";

const Context = createContext();

const ContextProvider = ({ children }) => {
  const [toggle, setToggle] = useState(true);
  const [about, setAbout] = useState(false);
  const [cart, setCart] = useState([]); // [{ ...product, qty }]

  const addToCart = (product) => {
    setCart((prev) => [...prev, { ...product, qty: 1 }]);
  };

  const updateQty = (id, delta) => {
    setCart((prev) =>
      prev
        .map((item) => (item.id === id ? { ...item, qty: item.qty + delta } : item))
        .filter((item) => item.qty > 0)
    );
  };

  return (
    <Context.Provider
      value={{ toggle, setToggle, about, setAbout, cart, setCart, addToCart, updateQty }}
    >
      {children}
    </Context.Provider>
  );
};

export { Context, ContextProvider };
```

### 2.1 Three Pieces of State, One Job Each

| State | Purpose |
|---|---|
| `toggle` | `true` → show the product grid; `false` → show the cart (used only when `about` is `false`) |
| `about` | `true` → show the About page, **overriding** whatever `toggle` says |
| `cart` | Array of cart items — each a full product object **plus** a `qty` field |

> Notice this is **not** a single `view` string (like `"home" | "about" | "cart"`) — it's two separate booleans (`toggle`, `about`) that combine to produce three possible views. This works, but it does mean there's an implicit priority order that isn't obvious just from the state names alone (see Section 3).

### 2.2 `addToCart` — Adding a New Item

```js
const addToCart = (product) => {
  setCart((prev) => [...prev, { ...product, qty: 1 }]);
};
```

- Uses the **functional updater** form (`prev => ...`), the safe pattern from your earlier batching notes.
- `[...prev, { ...product, qty: 1 }]` — spreads the existing cart array, then appends a **new object**: a full copy of the product (via `...product`), plus a `qty` field initialized to `1`. This is exactly why the code comment says the cart shape is `[{ ...product, qty }]` — each cart entry is the original product object's fields, extended with quantity tracking.
- **Note:** this function doesn't check whether the product is *already* in the cart — calling `addToCart` twice for the same product would add **two separate entries** with `qty: 1` each, rather than bumping one entry to `qty: 2`. In practice this doesn't happen in this app, because `ProductCard` (Section 5) only ever shows the "Add To Cart" button when the item **isn't already** in the cart — once it is, the UI switches to +/− controls instead, which call `updateQty`, not `addToCart`. So the "no duplicate check" gap is covered by the UI's own logic rather than by `addToCart` itself.

### 2.3 `updateQty` — Adjusting Quantity (and Auto-Removing at Zero)

```js
const updateQty = (id, delta) => {
  setCart((prev) =>
    prev
      .map((item) => (item.id === id ? { ...item, qty: item.qty + delta } : item))
      .filter((item) => item.qty > 0)
  );
};
```

This one function handles **three** different UI actions across the app, just by varying the `delta` argument:

| Call | Effect |
|---|---|
| `updateQty(id, 1)` | Increments that item's quantity by 1 |
| `updateQty(id, -1)` | Decrements that item's quantity by 1 |
| `updateQty(id, -item.qty)` | Passing the item's **entire current quantity** as a negative delta drops it straight to `0` in one call — this is how "Remove" is implemented (Section 6), without needing a separate `removeFromCart` function at all |

**How it works, step by step:**
1. **`.map(...)`** — walks every cart item; if its `id` matches the target `id`, returns a **new object** (`{ ...item, qty: item.qty + delta }`) with the adjusted quantity; every other item passes through unchanged.
   - This is the same reference-vs-mutation rule from your earlier state notes: `{ ...item, qty: ... }` creates a new object rather than mutating `item.qty` directly, which is required for React (and here, for the chained `.filter` below) to work correctly.
2. **`.filter((item) => item.qty > 0)`** — after the map, any item whose quantity dropped to `0` or below is **removed entirely** from the resulting array. This is the "auto-remove at 0" behavior noted in the code comment — decrementing a quantity down to zero (or explicitly removing via `-item.qty`) makes the item disappear from the cart automatically, with no separate delete logic needed.
3. The final chained result (`.map(...).filter(...)`) is a **brand-new array**, passed to `setCart` — again respecting the "always create new references" rule for state updates.

### 2.4 The Context `value` — One Big Bundle

```jsx
<Context.Provider value={{ toggle, setToggle, about, setAbout, cart, setCart, addToCart, updateQty }}>
```

- As covered in your earlier Context API notes, a Provider only accepts a single `value` — so all eight pieces (3 state values, their setters, plus the two derived cart functions) are bundled into one object.
- Notably, both the **raw setters** (`setToggle`, `setAbout`, `setCart`) **and** the **purpose-built functions** (`addToCart`, `updateQty`) are exposed here. Different consuming components use whichever is more convenient: `Navbar` uses the raw `setToggle`/`setAbout` directly (simple boolean flips), while `ProductCard`/`Cart` use the higher-level `addToCart`/`updateQty` (which encapsulate array logic that would be repetitive to write inline in every component that needs it).

## 3. `App.jsx` — Three-Way View Switching via Nested Ternary

```jsx
const App = () => {
  const [products, setProducts] = useState([]);
  const MyContext = useContext(Context);
  const { toggle, setToggle, about } = MyContext;

  const fetchData = async () => {
    try {
      const response = await axios.get("https://fakestoreapi.com/products");
      setProducts(response.data);
    } catch (error) {
      console.error(error);
    }
  };

  useEffect(() => {
    fetchData();
  }, []);

  return (
    <div className="min-h-screen bg-[#f7f4ec]">
      <Navbar />
      {about ? (
        <About />
      ) : toggle ? (
        <div className="max-w-7xl mx-auto p-4 grid grid-cols-1 sm:grid-cols-2 lg:grid-cols-3 xl:grid-cols-4 gap-6 items-stretch">
          {products.map((product) => (
            <ProductCard key={product.id} product={product} />
          ))}
        </div>
      ) : (
        <Cart />
      )}
    </div>
  );
};
```

### 3.1 `products` — Local State, Fetched Once

- `products` (the full product catalog from the Fake Store API) is **local** `useState` in `App`, **not** part of the context — it doesn't need to be shared with `Navbar`, and only `App` itself renders the grid, so there's no reason to lift it.
- `useEffect(() => { fetchData(); }, [])` — empty dependency array, so this fetch runs **exactly once**, on mount, following the same pattern from your earlier `useEffect` notes (and improving on the earlier `App.jsx` example, which had `[toggle]` as a dependency and consequently re-fetched unnecessarily on every view switch — here it correctly only fetches once).

### 3.2 The Nested Ternary — Three Views, Two Booleans

```jsx
{about ? (
  <About />
) : toggle ? (
  <ProductGrid />
) : (
  <Cart />
)}
```

Read as **priority order, top to bottom**:

1. **`about` is checked first.** If `true`, render `About` — **no matter what `toggle` is currently set to.** `about` effectively acts as an override switch on top of the `toggle` state.
2. **Only if `about` is `false`**, then `toggle` is checked: `true` → product grid, `false` → `Cart`.

This produces exactly **3 reachable views** from **2 booleans** (technically 4 combinations exist, but `about: true` always wins regardless of `toggle`'s value, collapsing two combinations into one visible result):

| `about` | `toggle` | Rendered |
|---|---|---|
| `true` | `true` | **About** |
| `true` | `false` | **About** (toggle is irrelevant here) |
| `false` | `true` | Product Grid |
| `false` | `false` | Cart |

> **Why this matters for `Navbar`:** since `about` overrides `toggle`, any button meant to leave the About page must explicitly set `about` back to `false` — simply changing `toggle` alone would have no visible effect while `about` is still `true`. This is exactly why, as you'll see in Section 4, both the "Home" and cart-icon click handlers in `Navbar` set **two** pieces of state together, not just one.

## 4. `Navbar.jsx` — Writing to the Shared View State

```jsx
const Navbar = () => {
  const { toggle, setToggle, setAbout, cart } = useContext(Context);

  return (
    <nav className="...">
      <img className="h-10" src="./ebay.svg" alt="eBay" />
      <div className="...">
        <span onClick={() => { setToggle(true); setAbout(false); }}>Home</span>
        <span onClick={() => { setAbout(true); }}>About</span>
      </div>
      <div className="relative">
        <img
          src="./cart.svg"
          onClick={() => { setToggle(false); setAbout(false); }}
        />
        {cart.length > 0 && (
          <span className="...">{cart.length}</span>
        )}
      </div>
    </nav>
  );
};
```

Three clickable elements, each writing a different combination of state:

| Element | Sets | Resulting view (per Section 3.2's table) |
|---|---|---|
| **"Home"** | `setToggle(true)`, `setAbout(false)` | Product Grid |
| **"About"** | `setAbout(true)` (toggle untouched) | About |
| **Cart icon** | `setToggle(false)`, `setAbout(false)` | Cart |

- The **"Home"** and **cart icon** handlers both explicitly set `setAbout(false)` — this is the direct consequence of the override behavior explained above: without resetting `about` back to `false`, clicking "Home" while already on the About page would silently do nothing visible, since `about: true` would keep winning the ternary regardless of `toggle`'s new value.
- **The cart badge:** `{cart.length > 0 && <span>{cart.length}</span>}` — the familiar conditional-rendering pattern, showing a small count bubble on the cart icon only when there's at least one item, reading directly from the shared `cart` array in context. Since `Navbar` reads `cart` via `useContext`, this badge automatically updates the instant any component calls `addToCart` or `updateQty` anywhere else in the app — no prop drilling, no manual syncing needed.

## 5. `ProductCard.jsx` — Per-Item Cart State Lookup

```jsx
export default function ProductCard({ product }) {
  useEffect(() => {
    loadFontsOnce();
  }, []);

  const { id, title, price, image, rating, category } = product;
  const { cart, addToCart, updateQty } = useContext(Context);
  const cartItem = cart.find((item) => item.id === id);

  // ...
}
```

### 5.1 `loadFontsOnce()` — A One-Time Side Effect Outside React State

```js
function loadFontsOnce() {
  if (document.getElementById("product-card-fonts")) return;

  const link = document.createElement("link");
  link.id = "product-card-fonts";
  link.rel = "stylesheet";
  link.href = "https://fonts.googleapis.com/css2?family=Fraunces:wght@500;600&...";

  document.head.appendChild(link);
}
```

- This function is called inside `useEffect(() => { loadFontsOnce(); }, [])` — a side effect, run once per `ProductCard` mount, exactly matching the `useEffect` patterns from your earlier notes.
- **The guard clause is important:** `if (document.getElementById("product-card-fonts")) return;` — since `ProductCard` is rendered **once per product** (potentially dozens of times in the grid), without this guard, every single card would try to inject its own `<link>` tag into `<head>`, duplicating the same Google Fonts stylesheet request over and over. The `id="product-card-fonts"` check ensures the font `<link>` is only ever actually added to the page **once**, no matter how many `ProductCard` instances mount.
- This is a case of **imperative DOM manipulation** living inside a `useEffect` — a reasonable escape hatch for something React doesn't have a first-class API for (dynamically injecting a stylesheet link), similar in spirit to how `useRef` was used earlier as an "escape hatch" to touch the DOM directly.

### 5.2 `cartItem` — Deriving Per-Card State From Shared Context

```js
const cartItem = cart.find((item) => item.id === id);
```

- `.find()` searches the **entire shared cart array** (from context) for an item matching *this specific* product card's `id`. If found, `cartItem` holds that cart entry (including its current `qty`); if not in the cart, `cartItem` is `undefined`.
- This is **derived state**, not stored state — `cartItem` isn't its own `useState`, it's recalculated fresh on every render directly from the context's `cart` array. This is a good instinct: since `cartItem` is fully computable from existing state (`cart` + this card's `id`), there's no need for a separate piece of state that could drift out of sync — recalculating it is cheap and always accurate.

### 5.3 Conditional UI — "Add to Cart" vs Quantity Controls

```jsx
{cartItem ? (
  <div className="...">
    <button onClick={() => updateQty(id, -1)}>−</button>
    <span>{cartItem.qty}</span>
    <button onClick={() => updateQty(id, 1)}>+</button>
  </div>
) : (
  <button onClick={() => addToCart(product)}>Add To Cart</button>
)}
```

- If `cartItem` exists (the product is already in the cart) → show a **quantity stepper** (`−`, current qty, `+`), each button calling `updateQty` with `±1`.
- If `cartItem` is `undefined` (not yet in the cart) → show a single **"Add To Cart"** button, calling `addToCart(product)`.
- This is exactly what prevents the "duplicate entries" gap mentioned in Section 2.2 — once an item is in the cart, its card **only ever** exposes `updateQty` buttons, never the "add" button again, so `addToCart` genuinely can't be called twice for the same product through the normal UI flow.
- **Decrementing to `0` via the `−` button**: since `updateQty`'s internal `.filter(item => item.qty > 0)` removes items at zero quantity, clicking `−` on a `qty: 1` item removes it from the cart entirely — and since `cartItem` is recalculated from the now-updated `cart` array on the next render, the card automatically flips back to showing the "Add To Cart" button again. No manual state syncing required — it's a natural consequence of `cartItem` being derived, not stored.

### 5.4 Small UI Details

```js
const words = title.split(" ");
const brand = words.slice(0, 3).join(" ");
const subtitle = words.slice(3).join(" ");
```
- Splits the product's full title into words, then arbitrarily treats the **first 3 words** as a "brand" heading and the **rest** as a subtitle — a simple, if slightly crude, string-based split used purely for visual formatting of the card (the Fake Store API doesn't provide a separate brand field, so this approximates one from the title text).

```js
{Array.from({ length: 5 }).map((_, i) => (
  <svg fill={i < full ? "#B5502A" : "none"} ... />
))}
```
- `Array.from({ length: 5 })` creates a throwaway array of 5 `undefined` slots purely to `.map()` over — a common trick for rendering a fixed number of repeated elements (5 star icons) without needing real data behind each one. `i < full` colors in stars up to the rounded rating value, leaving the rest outlined only.

## 6. `Cart.jsx` — Checkout Flow & Order Summary

```jsx
const Cart = () => {
  const { cart, updateQty, setCart } = useContext(Context);
  const [orderPlaced, setOrderPlaced] = useState(false);

  const subtotal = cart.reduce((sum, item) => sum + item.price * item.qty, 0);

  const handleCheckout = () => {
    setOrderPlaced(true);
    setCart([]);
  };

  if (orderPlaced) {
    return ( /* "Order Placed!" confirmation screen */ );
  }

  return ( /* cart items + order summary */ );
};
```

### 6.1 `subtotal` — Derived Total via `.reduce()`

```js
const subtotal = cart.reduce((sum, item) => sum + item.price * item.qty, 0);
```

- `.reduce()` walks the cart array, accumulating a running total: for each item, adds `price × qty` to the running `sum`, starting from `0`.
- Like `cartItem` in `ProductCard`, this is **derived state** — recalculated on every render directly from `cart`, never stored separately. If it were stored in its own `useState`, you'd have to remember to manually recompute and update it every time `cart` changed (in `addToCart`, in `updateQty`, in checkout) — a classic source of state going out of sync. Deriving it fresh each render guarantees it's always correct.

### 6.2 `orderPlaced` — Local State, Not Context

```js
const [orderPlaced, setOrderPlaced] = useState(false);
```

- Unlike `cart`/`toggle`/`about`, `orderPlaced` is **local** to `Cart` — no other component needs to know whether an order was just placed, so there's no reason to lift it into the shared context.

### 6.3 `handleCheckout` — Clearing the Cart

```js
const handleCheckout = () => {
  setOrderPlaced(true);
  setCart([]);
};
```

- Sets `orderPlaced` to `true` (switching `Cart`'s own render to the "Order Placed!" confirmation branch), and **empties the entire cart** via `setCart([])` — note this uses the **raw `setCart` setter** pulled straight from context, rather than `updateQty`, since clearing everything at once doesn't fit the per-item update pattern `updateQty` was built for.
- Because `cart` lives in shared context, this reset is instantly reflected everywhere — the `Navbar`'s cart badge disappears (`cart.length > 0` becomes `false`), and every `ProductCard` currently mounted would flip back to showing "Add To Cart" instead of quantity controls, since `cartItem` re-derives to `undefined` for every product.
- Clicking **"Continue Shopping"** on the confirmation screen (`onClick={() => setOrderPlaced(false)}`) simply returns `Cart` to its normal (now-empty) view — it doesn't touch `toggle`/`about`, so the user stays on the Cart view, just seeing the empty-cart state instead of the confirmation.

### 6.4 The "Remove" Button — Reusing `updateQty`

```jsx
<button onClick={() => updateQty(item.id, -item.qty)}>Remove</button>
```

- As explained in Section 2.3, this is the trick that avoids needing a dedicated remove function: passing the item's **own current quantity, negated**, guarantees the result of `qty + delta` is exactly `0`, which the `.filter(item.qty > 0)` step then strips from the array entirely — regardless of whether the item's quantity was `1`, `5`, or `20` at the time.

## 7. `About.jsx` — Pure Static Content

- No `useContext`, no `useState`, no props — a fully **static** page, built entirely from hardcoded content arrays (`stats`, `values`, timeline `items`, `team`, FAQ `items`) that are each `.map()`'d into repeated card layouts, following the exact same list-rendering pattern from your earlier "Movie Cards" module.
- Structurally, it's a good example of a page that **doesn't need** any shared state at all — it's included in the context-driven view-switching system (Section 3) purely because `App` needs to *decide whether to render it*, but once rendered, `About` itself is entirely self-contained.
- One small detail worth noting: every stat/value/timeline/team/FAQ array uses a **map with a natural unique key** (`stat.label`, `value.title`, `item.year`, `person.name`, `item.q`) rather than array index — consistent with the "prefer a stable, unique field over index" guidance from your earlier list-rendering notes.

## Quick Summary

```
Single Context as app-wide state:
  toggle, about, cart  → view control + cart data, all in ONE Context.Provider value

View switching (no router library):
  {about ? <About/> : toggle ? <Grid/> : <Cart/>}
  → `about` OVERRIDES `toggle` — must reset both together to fully "leave" About

Cart logic, centralized in context:
  addToCart(product)        → appends { ...product, qty: 1 }
  updateQty(id, delta)       → map to adjust qty, then filter out qty <= 0
                                (delta = -item.qty  ⇒  reused as "Remove")

Derived (not stored) state — recalculated fresh every render, never goes stale:
  cartItem = cart.find(item => item.id === id)     (ProductCard)
  subtotal = cart.reduce((sum, item) => ..., 0)     (Cart)

One-time DOM side effects via useEffect + a guard clause:
  loadFontsOnce() checks document.getElementById(...) first,
  so N mounted ProductCards only inject ONE <link> tag total.
```
