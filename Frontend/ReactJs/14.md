# React Router — BrowserRouter, Nested Routes & the Outlet/useMatch Pattern

This module covers a small multi-page app — a three-tab site (`Home`, `About`, `Contact`) with one **nested** route (`About → Details`) — built entirely on **React Router**, rather than the manual context-driven view-switching from the eBay module. Where that app used a single boolean pair (`toggle`/`about`) inside a Context to decide what to render, this app hands that same job off to the router: the **URL itself** is the source of truth for which view is showing.

---

## 1. Architecture Overview

```
main.jsx
  └── BrowserRouter        (owns: the URL ↔ UI sync, via the History API)
        └── App.jsx          (renders the persistent shell)
              ├── Navbar.jsx       (writes the URL, via <NavLink>)
              └── AppRoutes.jsx    (reads the URL → picks which page element to render)
                    ├── Home.jsx
                    ├── About.jsx
                    │     └── Details.jsx   (nested — rendered via <Outlet/>)
                    └── Contact.jsx
```

> Core idea: `BrowserRouter` owns the URL, `<Routes>`/`<Route>` decide *which* component renders for that URL, and `<Outlet>` decides *where inside a parent component* a matched **child** route renders. This is the router equivalent of the eBay app's nested ternary (`about ? <About/> : toggle ? <Grid/> : <Cart/>`) — same underlying idea of "pick one view based on current state," just with the browser's address bar as the state instead of two booleans in a Context.

---

## 2. Package Note: `react-router` vs `react-router-dom`

Every file in this app imports from **`react-router`**, not `react-router-dom`:

```js
import { NavLink } from "react-router";
import { BrowserRouter } from "react-router";
import { Routes, Route } from "react-router";
```

| | React Router v6 (older) | React Router v7 (current) |
|---|---|---|
| Web-specific package | `react-router-dom` | `react-router` (unified) |
| Core routing package | `react-router` | `react-router` (same package now) |
| Import for `BrowserRouter`, `Routes`, `Link`, `NavLink`, etc. | `from "react-router-dom"` | `from "react-router"` |
| `react-router-dom` still installable? | n/a | Yes, as a thin re-export for migration — scheduled for removal in v8 |

React Router v7 folded `react-router-dom`, `@remix-run/react`, and related packages into one unified `react-router` package, so every DOM API (`BrowserRouter`, hooks, components) now ships from that single import.

> If you paste in a Stack Overflow snippet that imports from `react-router-dom`, it will still *work* today (via the re-export) — but it's the older-style import. Worth knowing which one you're on before trusting a tutorial's import lines verbatim.

## 3. `main.jsx` — Entry Point & `BrowserRouter`

```jsx
import { createRoot } from "react-dom/client";
import "./index.css";
import App from "./App.jsx";
import { BrowserRouter } from "react-router";

createRoot(document.getElementById("root")).render(
  <BrowserRouter>
    <App />
  </BrowserRouter>
);
```

### 3.1 `createRoot(...).render(...)`

- The React 18+ root API (replaces the old `ReactDOM.render`) — enables concurrent features.

### 3.2 `<BrowserRouter>` — The Provider Every Router Feature Depends On

- Wraps the **entire** `<App />` tree. This is the piece that actually talks to the browser's History API (`pushState`/`popState`) to keep the URL bar in sync with your UI, without full page reloads.
- **Nothing below this line can use any router hook or component** (`useNavigate`, `NavLink`, `<Routes>`, etc.) unless it's inside this provider — the same "must be inside the Provider to consume it" rule from your Context notes (`ContextProvider` wrapping `App` in the eBay module), just for router state instead of app state.
- Only **one** `<BrowserRouter>` exists in the whole app (correct) — nesting multiple routers is a classic beginner mistake this code avoids.

## 4. `App.jsx` — The App Shell

```jsx
import React from 'react'
import Navbar from './components/Navbar'
import AppRoutes from './routes/AppRoutes'

const App = () => {
  return (
    <div className='h-screen flex flex-col'>
      <Navbar />
      <AppRoutes />
    </div>
  )
}

export default App
```

### 4.1 Layout

- `h-screen flex flex-col` — Tailwind classes making this a full-viewport-height flex column: `Navbar` sits on top, and whatever `AppRoutes` renders fills the rest. This is *why* `Home.jsx` and `Contact.jsx` (Section 6) use `flex-1` internally — they rely on this parent being a flex container to grow and fill remaining space.

### 4.2 `<Navbar />` Renders Outside `<Routes>`

- `Navbar` persists across every page because it sits in the shell, not inside the route tree — the manual equivalent of the eBay app always rendering its own `<Navbar />` above the `{about ? ... : ...}` ternary. React Router also has a formal way to express "persistent chrome around swappable content" — a **layout route** (a parent `<Route>` with no `path`, whose `element` renders `<Outlet />`) — but this code takes the simpler path of just placing `Navbar` in the shell, which is perfectly fine for a single global navbar.

### 4.3 Inferred Folder Structure

No file tree or `package.json` was uploaded, but these import paths only resolve with the following layout — **labeled as inferred**, from `./components/Navbar` and `./routes/AppRoutes` here, plus `../pages/...` inside `AppRoutes.jsx` (Section 5):

```
src/
├── main.jsx
├── App.jsx
├── index.css              (inferred — imported, not uploaded)
├── components/
│   └── Navbar.jsx
├── pages/
│   ├── Home.jsx
│   ├── About.jsx
│   ├── Contact.jsx
│   └── Details.jsx
└── routes/

```

## 5. `AppRoutes.jsx` — The Route Table

```jsx
import React from "react";
import { Routes, Route } from "react-router";
import Home from "../pages/Home";
import Details from "../pages/Details";
import About from "../pages/About";
import Contact from "../pages/Contact";

const AppRoutes = () => {
  return (
    <Routes>
      <Route path="/" element={<Home />} />
      <Route path="/about" element={<About />} >
        <Route path="details" element={<Details />} />
      </Route>
      <Route path="/contact" element={<Contact />} />
    </Routes>
  );
};

export default AppRoutes;
```

### 5.1 `<Routes>` — First Match Wins

- Scans its children and renders the **first** `<Route>` whose `path` matches the current URL. Order matters when paths could overlap (not an issue here — `/`, `/about`, `/contact` are all distinct).

### 5.2 The Nested `<Route>` — Where `/about/details` Actually Comes From

```jsx
<Route path="/about" element={<About />}>
  <Route path="details" element={<Details />} />
</Route>
```

| Piece | What it means |
|---|---|
| `path="details"` (no leading slash) | **Relative** to the parent — auto-prefixed, so the real matched URL is `/about/details` |
| Declaring this as a *child* of `/about`'s `<Route>` | Only produces a visible result if `About.jsx` itself renders `<Outlet />` somewhere (it does — see Section 7.3) |
| If you'd written `path="/details"` instead | It would **not** nest under `/about` — this is one of the most common nested-route mistakes |

> `<Route>` nesting and `<Outlet>` are two halves of one contract: the route table declares *that* a child can render there; `<Outlet />` in the parent component's own JSX declares *where*. Neither one alone produces anything on screen.

### 5.3 Gotcha — No Catch-All Route

None of the three page routes has a wildcard fallback (`path="*"`). Navigating to any unmatched URL (e.g. `/random-typo`) currently renders **nothing** — `<Routes>` returns `null` when no route matches. Worth adding `<Route path="*" element={<NotFound />} />` as the last entry so users get a real 404 instead of a blank screen.

## 6. Simple Page Components — `Home.jsx`, `Contact.jsx`, `Details.jsx`

### 6.1 `Home.jsx`

```jsx
import React from 'react'
import { Outlet } from 'react-router'

const Home = () => {
  return (
    <div className='flex-1 flex justify-center items-center'>
      <h1 className='text-white text-center text-7xl font-bold underline'>Home Page</h1>
    </div>
  )
}

export default Home
```

- `flex-1 flex justify-center items-center` — grows to fill the space left by `Navbar` (thanks to `App.jsx`'s `flex flex-col`), then centers its content both ways.
- **Bug worth calling out explicitly:** `import { Outlet } from 'react-router'` is **imported but never used** — `Home` has no nested child routes in `AppRoutes.jsx`, so there's nothing for an `<Outlet />` to render here. Dead code, most likely left over from copy-pasting `About.jsx` (which does need it) without trimming the unused import afterward. Harmless at runtime, but an ESLint `no-unused-vars` rule would flag it.

### 6.2 `Contact.jsx`

```jsx
import React from 'react'

const Contact = () => {
  return (
    <div className='flex-1 flex justify-center items-center'>
      <h1 className='text-white text-center text-7xl font-bold underline'>Contact Page</h1>
    </div>
  )
}

export default Contact
```

- Structurally identical to `Home.jsx` minus the unused `Outlet` import — this one's clean. A pure leaf page with no nested routes and no router hooks needed.

### 6.3 `Details.jsx`

```jsx
import React from 'react'

const Details = () => {
  return (
    <div className='flex justify-center items-center'>
      <h1 className='text-white text-center text-5xl font-bold'>&nbsp;&mdash;&gt; Details Page</h1>
    </div>
  )
}

export default Details
```

- No `flex-1` here, unlike `Home`/`Contact` — this is rendered by `<Outlet />` *inside* `About.jsx`'s layout (Section 7), not directly inside `App.jsx`'s flex column, so it doesn't need to independently claim remaining screen space the same way.
- `&nbsp;&mdash;&gt;` inside the JSX text — looks alarming at first glance, but **not a bug**: JSX text nodes decode standard HTML entities at compile time (via Babel's JSX transform), so this renders as `" —> Details Page"` (non-breaking space, em dash, greater-than sign), not as literal entity text. Just flagging it as intentional and working, since it's unusual to hand-write entities instead of typing the characters directly.

## 7. `About.jsx` — `Outlet`, `useMatch`, and `useNavigate` Working Together

```jsx
import React from "react";
import { NavLink, Outlet, useNavigate, useMatch } from "react-router";

const About = () => {
  const navigate = useNavigate();
  const onDetails = useMatch("/about/details");

  return (
    <div className="flex-1 flex justify-center items-center">
      <div className="relative">
        <h1 className="text-white text-center text-7xl font-bold underline">
          About Page
        </h1>
        {onDetails ? (
          <button
            className="text-emerald-500 top-0 -right-10 absolute font-bold hover:text-blue-500 cursor-pointer"
            onClick={() => navigate(-1)}
          >
            Back
          </button>
        ) : (
          <NavLink
            className="text-emerald-500 top-0 -right-10 absolute font-bold hover:text-blue-500"
            to="details"
          >
            Details
          </NavLink>
        )}
      </div>
      <Outlet />
    </div>
  );
};

export default About;
```

### 7.1 `useMatch` — Deriving "Am I Here?" Straight From the URL

```js
const onDetails = useMatch("/about/details");
```

- Checks whether the **current URL** matches the given pattern, relative to the app root. Returns a match object (truthy) when the current path is exactly `/about/details`, or `null` (falsy) otherwise.
- This is the same "derive state instead of storing a duplicate of it" instinct as `cartItem`/`subtotal` in the eBay module: instead of `About` keeping its own `const [showingDetails, setShowingDetails] = useState(false)` and manually toggling it in sync with navigation, it asks the router "what does the URL currently say?" and trusts that as the single source of truth. Nothing to keep in sync, no risk of the button and the actual route drifting apart.

### 7.2 The Conditional Render — Details Link vs Back Button

```jsx
{onDetails ? <button onClick={() => navigate(-1)}>Back</button>
           : <NavLink to="details">Details</NavLink>}
```

| State | Rendered | Behavior |
|---|---|---|
| Not on `/about/details` | `NavLink to="details"` | **Declarative** forward navigation — a link rendered directly in JSX |
| On `/about/details` | `button onClick={() => navigate(-1)}` | **Imperative** back navigation — a function called in response to a click |

- `to="details"` (no leading slash) is a **relative** link — resolved against `About`'s own route (`/about`), landing on `/about/details`. This matches the relative child path declared in `AppRoutes.jsx` (Section 5.2) — the link and the route table agree with each other.
- `navigate(-1)` is the router equivalent of the browser's Back button — it pops one entry off the session history stack, rather than navigating to a hardcoded destination like `navigate("/about")`.

> **Gotcha:** `navigate(-1)` depends on there being a *prior in-app history entry* to go back to. If a user lands directly on `/about/details` — via a bookmark, a shared link, or typing the URL fresh — there's nothing in-app to go back to, and `navigate(-1)` can behave unpredictably (potentially navigating the user out of the SPA entirely). A more defensive "Back" button would use the explicit `navigate("/about")` instead, unless true browser-Back semantics are specifically wanted.

### 7.3 `<Outlet />` — Where `Details` Actually Shows Up

- Placed at the bottom of `About`'s own JSX. This is what renders `<Details />` when the nested route matches.
- Remove this line and `Details` would still technically "match" per the route table (Section 5.2) — but nothing would visually appear; `About` would just render its header with no child content, silently. `<Outlet />` renders the matching child route's element, or nothing if there's no match.

## 8. `Navbar.jsx` — `NavLink` and the Missing "You Are Here" Styling

```jsx
import React from "react";
import { NavLink } from "react-router";

const Navbar = () => {
  return (
    <nav className="flex justify-between items-center px-5 py-3 text-white">
      <h1 className="text-2xl font-semibold">My App</h1>
      <div className="flex items-center justify-between gap-10 text-xl">
        <NavLink
          to={"/"}
          className="active:scale-95 transition-all duration-100 hover:underline hover:text-emerald-500 cursor-pointer"
        >
          Home
        </NavLink>
        <NavLink
          to={"/about"}
          className="active:scale-95 transition-all duration-100 hover:underline hover:text-emerald-500 cursor-pointer"
        >
          About
        </NavLink>
        <NavLink
          to={"/contact"}
          className="active:scale-95 transition-all duration-100 hover:underline hover:text-emerald-500 cursor-pointer"
        >
          Contact
        </NavLink>
      </div>
      <button className="bg-emerald-500 active:scale-95 transition-all duration-100 text-white font-bold py-2 px-4 rounded cursor-pointer">
        Login
      </button>
    </nav>
  );
};

export default Navbar;
```

### 8.1 Layout

- `flex justify-between items-center` on `<nav>` — a three-way split: logo on the left, links in the middle, Login button on the right, spread to the container's edges.

### 8.2 Why `NavLink` Instead of `Link` — And the Feature Left on the Table

- `NavLink` is used instead of plain `Link`, which is the right instinct: its whole purpose over `Link` is that it **automatically knows** whether it points at the currently-active route and exposes that to you. `NavLink` auto-applies active/pending state classes, and — more usefully — supports passing a **function** to `className` that receives `{ isActive, isPending }` so you can style the link conditionally yourself.

- **Bug worth calling out explicitly:** `className` on all three `NavLink`s here is a **plain string**, not a function:

  ```jsx
  <NavLink to="/about" className="... hover:underline hover:text-emerald-500 ...">
  ```

  Every link always gets the exact same class string regardless of which page is currently active — there is **no way for a user to tell which nav item corresponds to the page they're viewing** (no color/underline difference for the active tab). The `hover:` classes fire on mouse hover only, which isn't the same thing as an active-page indicator. Fix, matching the API's intended usage:

  ```jsx
  <NavLink
    to="/about"
    className={({ isActive }) =>
      `active:scale-95 transition-all duration-100 hover:underline hover:text-emerald-500 cursor-pointer ${
        isActive ? "text-emerald-500 underline" : ""
      }`
    }
  >
    About
  </NavLink>
  ```

  This is the same category of gap as the eBay app's cart badge working automatically off shared context — here, the *mechanism* to do it "for free" (`isActive`) exists and is imported, but the current code doesn't actually read it.

### 8.3 The Login Button

- `<button>Login</button>` has no `onClick` — presumably a placeholder ahead of auth being wired up, not a bug, just worth noting as non-functional in its current state.

## 9. Consolidated Issues & Gotchas Checklist

| File | Issue | Severity | Fix |
|---|---|---|---|
| `Home.jsx` | Unused `Outlet` import (no nested routes exist under `/`) | Low (dead code / lint warning) | Remove the import |
| `Navbar.jsx` | `NavLink`'s `className` is a static string — no visual "active page" indicator anywhere in the nav | Medium (UX gap; defeats the point of `NavLink` over `Link`) | Pass a function to `className` using `({ isActive }) => ...` |
| `AppRoutes.jsx` | No catch-all `path="*"` route | Medium (unmatched URLs silently render nothing) | Add `<Route path="*" element={<NotFound />} />` as the last route |
| `About.jsx` | `navigate(-1)` on the Back button assumes in-app history exists | Low–Medium (edge case: direct link/bookmark to `/about/details`) | Consider `navigate("/about")` for a guaranteed destination |

> None of these are "the app is broken" bugs — everything here renders and routes correctly as-is. They're the small gaps that are easy to miss on a first pass: missing active styling, no 404 route, and a stray unused import.
