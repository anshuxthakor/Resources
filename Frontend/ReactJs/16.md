# React Router — Data Mode: `createBrowserRouter`, Nested Routes & `Outlet`

Your earlier routing notes covered React Router's **declarative mode** (`<BrowserRouter>` + `<Routes>` + `<Route>` written directly as JSX). This module covers React Router's **other** setup style — **data mode**, using `createBrowserRouter` + `<RouterProvider>` — along with a genuinely new concept: **nested/layout routes** via `<Outlet>`.

---

## 1. Two Different Ways to Set Up Routing

| | Declarative Mode (earlier notes) | Data Mode (this app) |
|---|---|---|
| Setup | `<BrowserRouter><Routes><Route .../></Routes></BrowserRouter>` written as JSX | `createBrowserRouter([...])` — routes defined as a plain **JavaScript array of objects**, then rendered via `<RouterProvider router={router} />` |
| Where routes live | Directly in JSX, nested inside `<Routes>` | In a config array, passed to `createBrowserRouter` |
| Nesting | `<Route>` nested inside another `<Route>` in JSX | `children` array property on a route object |

<cite index="95-1">createBrowserRouter defines routes in a declarative manner, making it clear to manage complex routing structures, and supports data fetching and deferred loading at the route level</cite> — this data-centric config style is what unlocks React Router's more advanced data-loading features (`loader`, `action` functions) in larger apps, even though this particular example doesn't use those yet.

> **Both modes are valid, current React Router APIs** — this isn't "the old way vs the new way," it's two different configuration styles suited to different app complexity levels. Data mode tends to be favored as apps grow, since route configuration becomes centralized data rather than scattered JSX.

## 2. `AppRoutes.jsx` — The Router Configuration

```jsx
import React from 'react'
import { createBrowserRouter, RouterProvider } from 'react-router'
import MainLayout from '../layouts/MainLayout'
import Home from '../pages/Home'
import About from '../pages/About'
import Service from '../pages/Service'

const AppRoutes = () => {
  let router = createBrowserRouter([
    {
      path: "/",
      element: <MainLayout />,
      children: [
        { path: "", element: <Home /> },
        { path: "about", element: <About /> },
        { path: "service", element: <Service /> }
      ]
    }
  ])

  return <RouterProvider router={router} />
}

export default AppRoutes
```

### 2.1 `createBrowserRouter([...])` — Routes as Data

- Takes a single argument: an **array of route objects**. Each object typically has a `path`, an `element` (the component to render), and optionally a `children` array for nested routes.
- <cite index="87-1">createBrowserRouter uses the browser's history to handle navigation instead of reading it from the URL search string</cite> — the same underlying History API mechanism as `<BrowserRouter>` from declarative mode, just configured through a different API surface.
- The returned value (`router`) is not JSX — it's a **router instance object** that gets handed to `<RouterProvider>`.

### 2.2 `<RouterProvider router={router} />` — Activating the Router

- <cite index="95-1">RouterProvider is what unifies all the routing processes and settings of React Router — it serves as a facade to the routing capability of the app, connecting your component tree to the router instance so each part of the app gains access to routing.</cite>
- This is the **data-mode equivalent** of `<BrowserRouter>` — instead of wrapping your JSX tree in a provider component, you build a router object separately, then render `<RouterProvider>` with that object passed in as a prop.

### 2.3 The Nested Route Structure

```js
{
  path: "/",
  element: <MainLayout />,
  children: [
    { path: "", element: <Home /> },
    { path: "about", element: <About /> },
    { path: "service", element: <Service /> }
  ]
}
```

This is a **single top-level route object**, whose `children` array defines three nested routes underneath it. <cite index="82-1">Routes can be nested inside parent routes through children — the path of the parent is automatically included in the child, so this config creates both "/dashboard" and "/dashboard/settings" style URLs.</cite>

Applying that here:

| Child route config | Resulting full URL | Renders |
|---|---|---|
| `{ path: "", element: <Home/> }` | `/` (parent's own path, nothing appended) | `<Home />` |
| `{ path: "about", element: <About/> }` | `/about` | `<About />` |
| `{ path: "service", element: <Service/> }` | `/service` | `<Service />` |

### 2.4 The Empty-String Path (`path: ""`) — An Index Route, Written the Older Way

```js
{ path: "", element: <Home /> },
```

- Setting a child's `path` to an **empty string** means: render this child when the URL matches the **parent's own path exactly**, with nothing appended after it.
- <cite index="82-1">Index routes render into their parent's Outlet at their parent's URL, like a default child route.</cite> <cite index="83-1">index:true defines a default child route — it renders when the parent route is matched exactly, without any additional path.</cite>
- **Worth knowing:** the more modern, explicit way to write this same thing is `{ index: true, element: <Home /> }` (a boolean `index` property) rather than `{ path: "" }`. Both achieve the identical result — rendering `Home` at exactly `/` — but `index: true` is the form you'll see recommended in current official examples and documentation, since it makes the "this is the default child" intent explicit rather than relying on an easy-to-overlook empty string. This code's `path: ""` approach still works correctly; it's just the less commonly emphasized of the two equivalent forms.

## 3. `MainLayout.jsx` — A Layout Route & `<Outlet>`

```jsx
import React from "react";
import Navbar from "../components/Navbar";
import { Outlet } from "react-router";

const MainLayout = () => {
  return (
    <div className="flex flex-col min-h-screen bg-[#0F1115] text-[#E4E4E7] px-5 py-5">
      <Navbar />
      <main className="flex-1 flex items-center justify-center">
        <Outlet />
      </main>
    </div>
  );
};

export default MainLayout;
```

### 3.1 What Makes This a "Layout Route"

- Recall from Section 2.3 that `MainLayout` is the `element` for the **parent** route (`path: "/"`), and `Home`/`About`/`Service` are its `children`. This structure — a parent route whose only job is to render a shared shell (nav, footer, page padding) around whichever child route is currently active — is called a **layout route**.
- <cite index="84-1">This structure allows sharing headers, sidebars, and other layout elements while rendering different content based on the current route.</cite>

### 3.2 `<Outlet />` — Where the Child Route Actually Renders

- <cite index="82-1">Child routes are rendered through the Outlet in the parent route.</cite> <cite index="86-1">The Outlet component renders the matching child route with its respective component from the parent route's collection of child routes.</cite>
- Concretely: `MainLayout` always renders its `<Navbar />` and the outer `<div>`/`<main>` wrapper, **no matter which URL is active** — but wherever `<Outlet />` sits in its JSX is a **placeholder slot**, into which React Router drops whichever child route currently matches the URL (`Home`, `About`, or `Service`).
- This is the mechanism that makes `Navbar` **persistent across every page** in this app, without needing to import and render `<Navbar />` separately inside `Home.jsx`, `About.jsx`, and `Service.jsx` individually — you write the shared layout **once**, in `MainLayout`, and `<Outlet />` handles swapping just the inner content.

### 3.3 Comparing to Your Earlier (Declarative-Mode) App

In your previous React Router notes, `App.jsx` manually did this same "shared layout" job by hand:

```jsx
// From your earlier notes — declarative mode, no Outlet
const App = () => {
  return (
    <div className="flex flex-col gap-4">
      <Navbar />
      <AppRoutes />
    </div>
  );
};
```

- There, `Navbar` and the routed content (`<AppRoutes />`, which internally rendered `<Routes>`) were simply siblings placed next to each other directly in JSX — `Navbar` didn't need `<Outlet>` because it wasn't part of a *nested route relationship* with the pages; it was just a fixed sibling component in `App`.
- Here, in data mode, the relationship is formalized differently: `MainLayout` genuinely **is** a parent route in the router configuration, and `Home`/`About`/`Service` genuinely **are** its children — `<Outlet />` is the required mechanism for a parent *route* to render its matched child *route*, which is a different relationship than "two components sitting next to each other in JSX."
- **Practical upshot:** this nested-route approach scales more cleanly if you ever need **multiple different layouts** in one app (e.g. a `MainLayout` with a public navbar, and a separate `DashboardLayout` with a sidebar for logged-in areas) — each layout would be its own parent route with its own `children` array and its own `<Outlet />`, whereas the sibling-`Navbar`-in-`App` approach only really supports one single, app-wide layout shell.

## 4. `Navbar.jsx` — `NavLink`'s Active-Styling Function

```jsx
import React from "react";
import { NavLink } from "react-router";

const linkClasses = ({ isActive }) =>
  `transition-colors ${isActive ? "text-[#8B5CF6]" : "text-[#71717A] hover:text-[#E4E4E7] transition-all duration-100 active:scale-95"}`;

const Navbar = () => {
  return (
    <nav className="flex items-center justify-between text-2xl font-bold bg-[#191C22] rounded-3xl text-[#E4E4E7] px-5 py-4">
      <h1>Data Routing</h1>
      <div className="flex gap-10 text-xl">
        <NavLink to="/" className={linkClasses}>Home</NavLink>
        <NavLink to="/about" className={linkClasses}>About</NavLink>
        <NavLink to="/service" className={linkClasses}>Service</NavLink>
      </div>
    </nav>
  );
};

export default Navbar;
```

This is the piece your earlier `Navbar.jsx` **didn't** use, even though `NavLink` supports it — worth covering in full here.

### 4.1 `className` as a Function, Not a String

```jsx
<NavLink to="/" className={linkClasses}>Home</NavLink>
```

- Normally, `className` takes a plain string. `NavLink` specifically also accepts a **function** for `className` — <cite index="61-1">NavLink automatically applies an active CSS class (or a class you define) to the link when its route is currently active.</cite>
- React Router calls this function **for you**, automatically, passing in an object with an `isActive` boolean (among other properties) indicating whether **this specific `NavLink`'s `to` path matches the current URL**.

### 4.2 Reading `linkClasses` Itself

```js
const linkClasses = ({ isActive }) =>
  `transition-colors ${isActive ? "text-[#8B5CF6]" : "text-[#71717A] hover:text-[#E4E4E7] transition-all duration-100 active:scale-95"}`;
```

- `{ isActive }` — destructures the `isActive` boolean straight out of the object React Router passes in.
- Returns a **template-literal string** of Tailwind classes, conditionally including either:
  - The **active** styling (`text-[#8B5CF6]`, a purple accent color) when `isActive` is `true` — i.e., when this link's page is the one currently showing.
  - The **inactive/default** styling (gray text, hover-to-lighter-gray, plus press/hover transition classes) when `isActive` is `false`.
- **Result:** whichever nav item corresponds to the currently active page automatically gets highlighted in purple, with zero manual state tracking — no `useState` needed to track "which page is active," since `NavLink` derives it directly by comparing its own `to` path against the router's current URL, on every render.

## 5. `App.jsx` and `main.jsx` — A Structural Note

```jsx
// App.jsx
import React from 'react'

const App = () => {
  return (
    <div>
      <h1>Data Routing</h1>
    </div>
  )
}

export default App
```

```jsx
// main.jsx
import { createRoot } from "react-dom/client";
import "./index.css";
import AppRoutes from "./routes/AppRoutes.jsx";

createRoot(document.getElementById("root")).render(<AppRoutes />);
```

- **Worth flagging directly:** `App.jsx` is **never actually used anywhere** in this app. `main.jsx` renders `<AppRoutes />` directly as the root component — it never imports or renders `App` at all.
- This is very likely a leftover from an earlier stage of the project (perhaps the default Vite starter template, or an earlier iteration before routing was fully data-mode-ified) — `App.jsx` exists on disk and even has its own `<h1>Data Routing</h1>`, matching `Navbar`'s heading text, but it's fully dead code. It could be safely deleted, or `main.jsx` could be changed to render `<App />` (with `App` itself rendering `<AppRoutes />` internally) if you wanted to restore the more typical `main.jsx → App → routes` structure seen in your earlier, declarative-mode project.

## 6. Full Rendering Flow, End to End

```
main.jsx renders <AppRoutes/>
  → AppRoutes builds `router` via createBrowserRouter([...])
  → AppRoutes renders <RouterProvider router={router}/>

User visits "/"
  → router matches the top-level route (path: "/") → renders <MainLayout/>
  → MainLayout renders <Navbar/> + <main><Outlet/></main>
  → Outlet checks the URL again for a CHILD match → path: "" matches → <Home/>
  → Outlet renders <Home/> in its place
  → Navbar's "Home" NavLink → isActive: true → purple highlight

User clicks "About" in Navbar
  → NavLink navigates to "/about", no full page reload
  → router re-evaluates: parent route ("/") still matches → MainLayout stays mounted
  → child route "about" now matches → Outlet swaps its content to <About/>
  → Navbar itself does NOT re-render/remount (still part of MainLayout, untouched)
  → only Navbar's "About" NavLink's isActive flips to true → purple highlight moves
```

**A subtle but important detail:** because `MainLayout` (and therefore `Navbar`) lives at the **parent** route level, switching between `/`, `/about`, and `/service` **never unmounts `MainLayout` or `Navbar`** — only the content inside `<Outlet />` swaps. This is different from your earlier declarative-mode app, where the entire matched `<Route>` element (including anything conceptually "shared") would be replaced on every navigation, unless deliberately kept as a sibling outside `<Routes>`. Nested/layout routes make "persistent shell, swappable content" the default, structural behavior, rather than something you have to arrange manually.

## Quick Summary

```
Declarative mode (earlier notes):     Data mode (this app):
<BrowserRouter>                       createBrowserRouter([ {...} ])
  <Routes>                              → router instance (plain JS object)
    <Route path=".." element={} />
  </Routes>                           <RouterProvider router={router} />
</BrowserRouter>

Nested/layout routes:
  { path: "/", element: <Layout/>, children: [ {...}, {...} ] }
  → Layout is the PARENT route → renders shared shell + <Outlet/>
  → each child in `children` renders INTO that <Outlet/> slot
  → parent (and anything in it, like Navbar) stays mounted across child navigations

Index route:
  { path: "" , element: <Home/> }         (works, but implicit)
  { index: true, element: <Home/> }       (equivalent, more explicit/modern form)
  → renders at the parent's own exact URL, no extra path segment

NavLink active styling:
  <NavLink to="/x" className={({isActive}) => isActive ? "..." : "..."} />
  → React Router calls your function automatically, passing isActive
  → no manual useState/tracking needed to know "which page is current"
```
