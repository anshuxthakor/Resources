# React Router (Data Mode) — Auth Flow, Protected Routes & Axios Interceptors

This module covers a full authentication-gated app — login/register, a protected `/main` area with its own sidebar shell, and two data-fetched list pages (Products, Users). It pulls together three things from earlier modules and adds two new ones: **Context** (Module 1's state-lifting pattern, now holding auth state instead of a cart), **`Outlet`/`useNavigate`/`NavLink`** (Module 2, now with the active-state styling actually wired up), plus **React Hook Form**, **Axios interceptors**, and React Router's **data router API** (`createBrowserRouter` + `RouterProvider`) — a different, newer way of declaring routes than Module 2's JSX-based `<Routes>`/`<Route>`.

---

## 1. Architecture Overview

```
main.jsx
  └── AuthProvider          (Context: registeredUser, loggedInUser + setters — persisted to localStorage)
        └── AppRoutes.jsx     (creates a router via createBrowserRouter, renders it via <RouterProvider>)
              │
              ├── "/"          → AuthLayout          (redirects AWAY if already logged in)
              │      └── ""    → Login
              ├── "/register"  → Register              (⚠ not guarded by AuthLayout — see §7.3)
              │
              └── "/main"      → ProtectedRoutes       (redirects AWAY if NOT logged in)
                     └── ""    → MainLayout             (sidebar shell: Navbar + content panel)
                            ├── ""          → Home
                            ├── "users"     → Users
                            └── "products"  → Products
        └── ToastContainer    (react-toastify's notification portal, sibling to AppRoutes)
```

> Same underlying idea as Module 1's `ContextProvider` and Module 2's `BrowserRouter`: everything that needs shared auth state or routing must live *inside* the relevant provider. Here that's doubly true — `AuthProvider` wraps the whole app, and the router itself is created and consumed via `RouterProvider`, not the `<BrowserRouter>` component from Module 2.

## 2. New API Note: Data Router (`createBrowserRouter`) vs Declarative Router (`<Routes>`)

Module 2's app declared routes as JSX:

```jsx
<BrowserRouter>
  <Routes>
    <Route path="/about" element={<About />}>
      <Route path="details" element={<Details />} />
    </Route>
  </Routes>
</BrowserRouter>
```

This app declares the same *shape* of nesting, but as a plain JavaScript array of route objects, fed into `createBrowserRouter`, then rendered with `<RouterProvider>`:

```jsx
let router = createBrowserRouter([
  { path: "/main", element: <ProtectedRoutes />, children: [ /* ... */ ] },
]);
return <RouterProvider router={router} />;
```

| | Declarative mode (Module 2) | Data mode (this module) |
|---|---|---|
| How routes are declared | JSX (`<Routes>`/`<Route>`) | Plain object array (`RouteObject[]`) |
| Top-level wrapper | `<BrowserRouter>` component | `createBrowserRouter(...)` creates a router instance; `<RouterProvider router={router}>` renders it |
| Nesting | `<Route>` inside `<Route>` | `children` array inside a route object |
| Enables loaders/actions/fetchers (v6.4+ data APIs) | No | Yes |
| Where the router is created | Anywhere in the tree, declaratively, each render | **Once**, outside/before the component tree ideally — official docs are explicit that *"Data Routers should not be held in React state… create your router once."* |

> **Worth flagging:** `AppRoutes.jsx` calls `createBrowserRouter([...])` **inside** the `AppRoutes` function component's body, meaning a brand-new router object is technically constructed on every render of `AppRoutes`. In practice this component only renders once (it has no props/state that would cause re-renders here), so it isn't actively breaking anything — but it's worth knowing the official guidance is to hoist route creation *outside* the component function entirely, so the router is guaranteed to be a stable, single instance no matter what else changes in the tree above it.

## 3. `axiosInstance.jsx` — Axios Interceptors

```jsx
import axios from "axios";

export const axiosInstance = axios.create({
  baseURL: "https://fakestoreapi.com"
});

axiosInstance.interceptors.request.use(
  (config) => {
    console.log("API Interceptors Request —> ", config);
    return config;
  },
  (error) => {
    console.error("API Interceptors Request Error —> ", error);
    return Promise.reject(error);
  }
);

axiosInstance.interceptors.response.use(
  (response) => {
    console.log("API Interceptors Response —> ", response);
    return response;
  },
  (error) => {
    console.error("API Interceptors Error —> ", error);
    return Promise.reject(error);
  }
);
```

### 3.1 `axios.create({ baseURL })`

- Produces a **configured instance** of axios, rather than using the global `axios` object directly. Every call made through `axiosInstance` (see `Products.jsx`/`Users.jsx`, §11) can use a relative path like `axiosInstance.get("/products")`, which axios expands against `baseURL` into the full `https://fakestoreapi.com/products` URL. This means the base URL lives in exactly one place — if it ever needs to change, nothing in `Products.jsx` or `Users.jsx` has to.

### 3.2 Interceptors — Middleware for Every Request/Response

- `.interceptors.request.use(onFulfilled, onRejected)` — runs `onFulfilled` on **every outgoing request** before it's actually sent, and `onRejected` if something goes wrong *building* the request (rare, but possible — e.g. a bad config).
- `.interceptors.response.use(onFulfilled, onRejected)` — runs `onFulfilled` on **every incoming response** before your `.then()`/`await` code sees it, and `onRejected` whenever a request fails (network error, non-2xx status, etc.).
- As written, both interceptor pairs do exactly one thing: `console.log` the config/response, or `console.error` the failure, then **pass the value through unchanged** (`return config;` / `return response;` / `return Promise.reject(error);`). This is the standard "no-op passthrough with logging" skeleton — the useful part is that this is the *one place* you'd later add real cross-cutting behavior (e.g. attaching an auth token header to every request, or redirecting to login on a 401 response) without touching `Products.jsx`, `Users.jsx`, or any future page that uses `axiosInstance`.
- **Worth reconsidering before shipping:** logging the full request `config` and response objects to the console on *every* API call is useful during development but is dead weight (and occasionally a minor information-leak risk, e.g. exposing full request/response payloads in the browser console) in production. Since none of this app's auth is real (see §5 below — auth is entirely client-side, no token to leak here), it's low-stakes right now, but it's a habit worth dropping once real request headers or tokens are involved.

## 4. `AuthContext.jsx` — Auth State, Persisted to `localStorage`

```jsx
import { createContext, useState } from "react";

export const Auth = createContext();

export const AuthProvider = ({ children }) => {
  const [registeredUser, setRegisteredUser] = useState(
    JSON.parse(localStorage.getItem("registeredUser")) || [],
  );
  const [loggedInUser, setLoggedInUser] = useState(
    JSON.parse(localStorage.getItem("loggedInUser")) || null,
  );

  console.log("Logged In User —> ", loggedInUser);

  return (
    <Auth.Provider
      value={{
        registeredUser,
        setRegisteredUser,
        loggedInUser,
        setLoggedInUser,
      }}
    >
      {children}
    </Auth.Provider>
  );
};
```

### 4.1 Lazy-ish Initial State from `localStorage`

```js
useState(JSON.parse(localStorage.getItem("registeredUser")) || [])
```

- `localStorage.getItem("registeredUser")` returns either a JSON string (if something was saved previously) or the actual value `null` (if the key was never set).
- `JSON.parse(null)` looks alarming but is **not a bug** — `JSON.parse` coerces its argument to a string first, and the string `"null"` parses validly to the JS value `null`. So on a fresh browser with nothing saved yet, this line safely evaluates to `null || []` → `[]`. Worth knowing this works *because* of that specific coercion quirk, not because `JSON.parse` gracefully "handles" `null` in some more general sense — feeding it `undefined` instead, for example, throws.
- Same pattern for `loggedInUser`, defaulting to `null` instead of `[]`, matching what `setLoggedInUser` is meant to hold (a single user object or nothing).
- This is the same "the app should survive a first-ever load with no prior data" instinct as `useState([])` for `cart` in the eBay module (Module 1) — just extended here to also **survive a page refresh**, by reading from `localStorage` instead of always starting empty. Plain `useState` alone resets on every reload; reading from `localStorage` inside the initializer is what makes the login persist across refreshes.

### 4.2 Worth Reconsidering — Plaintext Passwords in `localStorage`

- `registeredUser` stores whatever `Register.jsx`'s form submits (§10.2) directly, unmodified — including the **plaintext password field** — straight into `localStorage`. Anyone with access to the browser's DevTools (Application → Local Storage) can read every registered user's password in cleartext. For a learning project against a fake API with no real backend, this is a reasonable simplification — but it's worth flagging explicitly as something that would never be acceptable once a real backend/auth token is involved: passwords should never round-trip through client storage at all, let alone in plaintext.
- Similarly, `console.log("Logged In User —> ", loggedInUser)` runs on **every single render** of `AuthProvider` (i.e., very often, since `AuthProvider` wraps the entire app) and logs the full user object — including that same password field — to the browser console. Harmless for local development, but another habit worth dropping before anything resembling production.

### 4.3 The Context `value` — Only Raw Setters, No Derived Functions

- Unlike the eBay module's `Context.Provider`, which bundled both raw setters (`setCart`) **and** purpose-built functions (`addToCart`, `updateQty`) into one `value`, this Provider exposes **only** the raw state and setters (`registeredUser`, `setRegisteredUser`, `loggedInUser`, `setLoggedInUser`) — no `login()`/`register()`/`logout()` functions live here. That logic instead lives one layer out, in the `useAuth` custom hook (§5) — a different way of splitting responsibility than the eBay app's, worth noticing as a **design choice**, not a right/wrong: here, the Context is a thin data store, and a separate hook composes it with form handling and navigation.

## 5. `useAuth.jsx` — A Custom Hook Composing Context + Forms + Navigation

```jsx
import { useContext } from "react";
import { toast } from "react-toastify";
import { useForm } from "react-hook-form";
import { useNavigate } from "react-router";
import { Auth } from "../context/AuthContext";

export const useAuth = () => {
  const navigate = useNavigate();
  const {
    register,
    handleSubmit,
    reset,
    formState: { errors },
  } = useForm();
  const { registeredUser, setRegisteredUser, loggedInUser, setLoggedInUser } =
    useContext(Auth);

  const loginFormSubmit = (data) => {
    let user = registeredUser.find(
      (val) => val.username === data.username && val.password === data.password,
    );
    if (!user) {
      toast.error("Invalid username or password");
      reset();
      return;
    }
    setLoggedInUser(user);
    localStorage.setItem("loggedInUser", JSON.stringify(user));
    toast.success("Login successful");
    reset();
    navigate("/main");
  };

  const registerFormSubmit = (data) => {
    let arr = [...registeredUser, data];
    setRegisteredUser(arr);
    localStorage.setItem("registeredUser", JSON.stringify(arr));
    setLoggedInUser(data);
    localStorage.setItem("loggedInUser", JSON.stringify(data));
    navigate("/login");
    toast.success("Account created successfully");
    reset();
  };

  return {
    register,
    handleSubmit,
    reset,
    navigate,
    errors,
    registerFormSubmit,
    loginFormSubmit,
  }
};
```

### 5.1 This Is a "Custom Hook," Not Just a Helper Function

- Because it calls other hooks internally (`useNavigate`, `useForm`, `useContext`), `useAuth` **must** follow the Rules of Hooks itself — it can only be called from the top level of a React component (or another custom hook), never conditionally or inside a loop. It's essentially a **bundle**: one call gives `Login.jsx`/`Register.jsx` everything they need (form bindings, error state, submit handlers, navigation) without either page having to individually wire up `useForm`, `useContext(Auth)`, and `useNavigate` on its own.

### 5.2 `loginFormSubmit` — Linear Search Through `registeredUser`

```js
let user = registeredUser.find(
  (val) => val.username === data.username && val.password === data.password,
);
```

- `.find()` walks the `registeredUser` array (from Context) looking for the **first** entry whose `username` *and* `password` both match what was typed into the login form. If nothing matches, `user` is `undefined`, and the `if (!user)` branch fires an error toast and resets the form without navigating anywhere.
- On success: updates `loggedInUser` in Context, **also** manually mirrors that same value into `localStorage.setItem("loggedInUser", ...)`, shows a success toast, resets the form, and finally calls `navigate("/main")` — an **imperative** redirect (the function-call style from Module 2's `navigate(-1)`), as opposed to the **declarative** `<Navigate>` component used in the route guards (§7).
- **Worth reconsidering:** since this app has no real backend, "authentication" here is just an array scan for a matching username+password pair stored in plaintext (see §4.2) — fine for a demo, but this is the client-only-fake-auth pattern, not real authentication. There's no password hashing, no server verifying credentials, nothing a real login screen would need.

### 5.3 `registerFormSubmit` — Same Gap as the eBay App's `addToCart`

```js
let arr = [...registeredUser, data];
setRegisteredUser(arr);
```

- Spreads the existing `registeredUser` array and appends the new form `data` — the same "always create a new array reference, never mutate" rule from the eBay module's `addToCart`/`updateQty`.
- **Bug worth calling out explicitly, and it's the same shape of gap as `addToCart` in Module 1:** this function does **not** check whether the submitted `username` already exists in `registeredUser` before appending. Two people (or the same person twice) can register the exact same username, creating two separate entries. Because `loginFormSubmit` uses `.find()` (§5.2), which always returns the **first** match, only the *first*-registered account with that username would ever be reachable via login afterward — the duplicate would silently become permanently unloggable-into. In the eBay app, this exact class of gap (no duplicate check in `addToCart`) turned out to be harmless because the UI itself prevented the duplicate call; here, nothing in `Register.jsx`'s form validation (§10.2) checks for an existing username, so this one is a real, reachable gap worth fixing — e.g. checking `registeredUser.some(u => u.username === data.username)` before appending, and showing a toast error if so.
- On success: appends to `registeredUser`, **also immediately logs the new user in** (`setLoggedInUser(data)`), persists both to `localStorage`, but then calls `navigate("/login")` — sending a user who *is already logged in* to the login page. Since `/login` in this app's route tree is actually served at path `""` under `AuthLayout` (§7.2), and `AuthLayout` redirects logged-in users straight to `/main` (§7.1), this works out fine in practice — the user briefly "visits" `/login`'s path but is immediately bounced onward by the guard — but it's a slightly roundabout way to get there compared to just calling `navigate("/main")` directly, given the user is already logged in at that point.

## 6. Route Guards: `AuthLayout.jsx` vs `ProtectedRoutes.jsx`

These two components are mirror images of each other — both read `loggedInUser` from Context and both render `<Outlet />` when nothing needs to happen, but they guard in **opposite directions**.

### 6.1 `AuthLayout.jsx` — Keep Logged-In Users OUT of Auth Pages

```jsx
import React, { useContext } from 'react'
import { Auth } from '../context/AuthContext'
import { Navigate, Outlet } from 'react-router'
import { toast } from 'react-toastify';

const AuthLayout = () => {
  const { loggedInUser } = useContext(Auth);

  if (loggedInUser) {
    return <Navigate to="/main" />;
  }

  return <Outlet />;
};

export default AuthLayout;
```

### 6.2 `ProtectedRoutes.jsx` — Keep Logged-Out Users OUT of the App

```jsx
import React, { useContext } from 'react'
import { Auth } from '../context/AuthContext'
import { Navigate, Outlet } from 'react-router'
import { toast } from 'react-toastify';

const ProtectedRoutes = () => {
  const { loggedInUser } = useContext(Auth);

  if (!loggedInUser) {
    return <Navigate to="/" />;
  }

  return <Outlet />;
};

export default ProtectedRoutes;
```

| | `AuthLayout` | `ProtectedRoutes` |
|---|---|---|
| Guards | `/` (→ Login) | `/main` and everything under it |
| Condition | `if (loggedInUser)` — user **is** logged in | `if (!loggedInUser)` — user is **NOT** logged in |
| Redirects to | `/main` | `/` |
| Otherwise renders | `<Outlet />` → lets `Login` through | `<Outlet />` → lets `MainLayout` (and its children) through |

### 6.3 `<Navigate>` — Declarative Redirect, Used at the Route-Guard Layer

- `<Navigate to="..." />` is a **component**, not a function — rendering it is itself the act of triggering a redirect, evaluated during render rather than called from an event handler. This is the same declarative-vs-imperative distinction from Module 2 (`NavLink` vs `useNavigate`), just applied one level up: here, the entire *decision* of "should this route be allowed to render at all?" is expressed declaratively, as JSX, rather than as an imperative check-and-redirect inside a `useEffect`.
- Both guard components import `toast` from `react-toastify` but **never actually call it** — dead import in both files. A natural place to *use* it would be showing a toast like `"Please log in to continue"` right before the `<Navigate to="/" />` redirect in `ProtectedRoutes` — currently the redirect happens silently, with no explanation to the user for why they landed back on the login page.

## 7. `AppRoutes.jsx` — The Nested Route Tree

```jsx
import React from "react";
import { createBrowserRouter, RouterProvider } from "react-router";
import MainLayout from "../layouts/MainLayout";
import Home from "../pages/Home";
import Users from "../pages/Users";
import Products from "../pages/Products";
import AuthLayout from "../layouts/AuthLayout";
import Register from "../pages/auth/Register";
import Login from "../pages/auth/Login";
import ProtectedRoutes from "./ProtectedRoutes";

const AppRoutes = () => {
  let router = createBrowserRouter([
    {
      path: "/",
      element: <AuthLayout />,
      children: [
        {
          path: "",
          element: <Login />,
        },
      ],
    },
    {
      path: "/register",
      element: <Register />,
    },
    {
      path: "/main",
      element: <ProtectedRoutes />,
      children: [
        {
          path: "",
          element: <MainLayout />,
          children: [
            {
              path: "",
              element: <Home />,
            },
            {
              path: "users",
              element: <Users />,
            },
            {
              path: "products",
              element: <Products />,
            },
          ],
        },
      ],
    },
  ]);
  return <RouterProvider router={router} />;
};

export default AppRoutes;
```

### 7.1 Three Levels of Nesting Under `/main` — Two Different *Purposes* of Layout

```
"/main"  → ProtectedRoutes   (guard layer — no visible UI, just an Outlet or a redirect)
  ""     → MainLayout        (visual layer — sidebar + bordered content panel, renders its own Outlet)
    ""          → Home
    "users"     → Users
    "products"  → Products
```

- `ProtectedRoutes` and `MainLayout` are **both** "layout routes" (routes whose `element` renders an `<Outlet />` for children) in the technical React Router sense, but they serve genuinely different jobs: `ProtectedRoutes` exists purely as a **gatekeeper** (renders nothing of its own — either a redirect or a bare `Outlet`), while `MainLayout` (§8) is the actual **visual shell** (sidebar nav + bordered panel) that the guarded pages render inside of. Stacking them lets the guard logic live completely separately from the UI chrome — `MainLayout` never has to know or care whether the user is logged in; by the time anything reaches it, `ProtectedRoutes` has already handled that.
- Both `{ path: "", element: <AuthLayout>'s child }` and `{ path: "", element: <MainLayout> }` use an **empty string path** to mean "matches the parent's path exactly, with nothing appended" — this is the data-router object equivalent of Module 2's relative child paths (`path="details"` under `/about`), just expressed as `""` instead of omitting a segment.

### 7.2 `/register` Is a Top-Level Route, Not Nested Under `AuthLayout`

```js
{ path: "/", element: <AuthLayout />, children: [{ path: "", element: <Login /> }] },
{ path: "/register", element: <Register /> },
```

- **Gotcha worth flagging explicitly:** `Login` is nested under `AuthLayout` (so a logged-in user hitting `/` gets bounced to `/main`), but `Register` sits at the **top level**, completely outside `AuthLayout`'s guard. This means an already-logged-in user who manually navigates to `/register` (typing the URL, or via a stale bookmark) is **not** redirected away — they'd see the registration form and could submit it, silently overwriting their `loggedInUser` in Context/`localStorage` with a brand-new account (per §5.3's `registerFormSubmit`, which always calls `setLoggedInUser(data)` unconditionally). Wrapping `/register` under `AuthLayout` alongside `/` would close this gap and match the way `/` already behaves.

### 7.3 No Catch-All Route Here Either

- Same gotcha as Module 2's `AppRoutes.jsx`: none of these routes has a `path: "*"` fallback. An unmatched URL renders nothing — worth adding one as the last top-level entry.

## 8. `MainLayout.jsx` — The Authenticated Shell

```jsx
import { Outlet } from "react-router";
import Navbar from "../components/Navbar";

const MainLayout = () => {

        backgroundColor: "#eef1f4",
        backgroundImage:
          "linear-gradient(#d7dee5 1px, transparent 1px), linear-gradient(90deg, #d7dee5 1px, transparent 1px)",
        backgroundSize: "26px 26px",
      }}
    >
      <Navbar />

      <div className="relative h-full min-h-0">
        <span className="absolute -top-2 -left-2 h-4 w-4 border-t-2 border-l-2 border-[#d7263d]" />
        <span className="absolute -top-2 -right-2 h-4 w-4 border-t-2 border-r-2 border-[#d7263d]" />
        <span className="absolute -bottom-2 -left-2 h-4 w-4 border-b-2 border-l-2 border-[#d7263d]" />
        <span className="absolute -bottom-2 -right-2 h-4 w-4 border-b-2 border-r-2 border-[#d7263d]" />

        <div className="bg-white border-[1.5px] border-[#16324f] h-full px-6 py-5 overflow-auto scrollbar-none [-ms-overflow-style:none] [&::-webkit-scrollbar]:hidden">
          <Outlet />
        </div>
      </div>
    </div>
  );
};

export default MainLayout;
```

### 8.1 `grid-cols-[260px_1fr]` — Fixed Sidebar, Fluid Content

- A two-column CSS grid: `Navbar` gets a fixed `260px` column, and everything else (the content panel) takes up the remaining space (`1fr`). This is a different layout strategy than the eBay/Router modules' `flex` columns — grid is a natural fit here specifically *because* the two regions need genuinely different sizing rules (fixed vs fluid), where flex's `flex-1` growing-to-fill behavior from earlier modules would need more fighting to pin the sidebar to an exact width.

### 8.2 The Four Corner `<span>`s — Decorative "Blueprint" Corner Brackets

- Four absolutely-positioned `<span>` elements, one per corner, each with only two of its four border sides colored (`border-t-2 border-l-2`, etc.) — this draws small open bracket marks at each corner of the panel rather than a full border, matching the "technical drawing / spec sheet" visual language mentioned in `Home.jsx` (§13). Purely decorative, no functional role.

### 8.3 `<Outlet />` — Where `Home`/`Users`/`Products` Actually Render

- Same mechanism as Module 2's `About.jsx` — `MainLayout` is a parent route's `element`, and whichever child route currently matches (`Home`, `Users`, or `Products`, per §7.1) renders wherever this `<Outlet />` sits, nested one level inside the bordered content panel.

## 9. `Navbar.jsx` & `NavItem.jsx` — `NavLink`'s Active-State Fix From Module 2

Module 2 flagged that its `Navbar.jsx` passed `NavLink` a **static string** `className`, meaning no page ever visually appeared "active" in the nav. This module's `NavItem.jsx` is the fix for exactly that gap — worth reading side-by-side with Module 2's callout.

- Renders three `NavItem`s (§9.2 does the real work) plus a **Sign out** button. Signing out does three things together: removes `loggedInUser` from `localStorage`, fires a warning toast, and clears `loggedInUser` in Context via `setLoggedInUser(null)` — that last call is what actually causes `ProtectedRoutes` (§6.2) to re-evaluate `if (!loggedInUser)` on next render and redirect back to `/`.
- **Minor inconsistency worth noting:** `setRegisteredUser`'s corresponding entry is left untouched here — signing out only clears *session* state (`loggedInUser`), not the registered-accounts list, which is correct (you don't want signing out to delete the account) but worth being explicit about, since `AuthContext.jsx` doesn't otherwise document which piece of state each action is supposed to touch.

### 9.2 `NavItem.jsx` — `className` *and* `children` as Functions

```jsx
import React from "react";
import { NavLink } from "react-router";

const NavItem = ({ to, end, letter, children }) => {
  return (
    <NavLink
      to={to}
      end={end}
      className={({ isActive }) =>
        `flex items-center gap-2 font-mono text-[11px] uppercase tracking-[0.15em] py-1.5 pl-2 border-l-2 transition-colors ${
          isActive
            ? "border-[#d7263d] text-[#d7263d] font-bold"
            : "border-transparent text-[#16324f] hover:text-[#d7263d] hover:border-[#d7263d]/40"
        }`
      }
    >
      {({ isActive }) => (
        <>
          <span
            className={`flex items-center justify-center h-4 w-4 border text-[9px] shrink-0 ${
              isActive
                ? "border-[#d7263d] text-[#d7263d]"
                : "border-[#16324f] text-[#16324f]"
            }`}
          >
            {letter}
          </span>
          {children}
        </>
      )}
    </NavLink>
  );
};

export default NavItem;
```

- **This is the exact fix Module 2's writeup called for.** `className` is now a **function** receiving `{ isActive }`, exactly matching `NavLink`'s documented render-prop signature — active links get a colored left border, bold red text; inactive ones get a transparent border and only pick up color on hover. React Router's official docs confirm this is the intended usage: `className` can be a plain string *or* a function of `{ isActive, isPending }`, and using the function form is precisely how you get per-link "you are here" styling instead of every link looking identical regardless of route.
- **`children` as a function too** — this is a step further than just `className`. `NavLink` also accepts its `children` as a function of `{ isActive }` (documented as a "render prop"), which is what lets the little lettered badge (`<span>{letter}</span>`) *also* change color when active, not just the surrounding link text. Passing a function to `children` and reading `isActive` from its argument, exactly like the `className` callback, is what makes this possible — regular JSX children (a plain string/elements, as Module 2's `Navbar` used) have no way to know the link's own active state.
- **`end` prop — why `/main`'s `NavItem` has it and the others don't:**

  ```jsx
  <NavItem to="/main" end letter="A">Home</NavItem>
  <NavItem to="/main/products" letter="B">Products</NavItem>
  ```

  By default, `NavLink` treats a link as active if the current URL **starts with** its `to` path — so without `end`, `/main` would count as "active" on `/main`, `/main/products`, *and* `/main/users` all at once, since all three start with `/main`. The `end` prop restricts the match to the **exact** path (or, more precisely, changes the matching to only match "to the end" of the `to` path), so the Home link only lights up when the URL is exactly `/main`, not on any of its sub-pages. `/main/products` and `/main/users` don't need `end` because nothing else in this route tree starts with those longer, more specific paths.

```jsx
          label="username"
          type="text"

              message: "must include a letter and a number",
            },
          })}
        />
        <button
          type="submit"
          className="w-full bg-[#16324f] text-white text-sm font-bold uppercase tracking-wide py-2.5 hover:bg-[#d7263d] active:scale-95 transition-all duration-100 cursor-pointer mt-1"
```

- Same structural pattern as `Login`, three fields instead of two. Each field's `pattern` regex is worth reading individually since they're doing real validation work:
  - `name`: `/^[A-Za-z\s]+$/` — letters and whitespace only (blocks digits/symbols in a name field).
  - `username`: `/^[a-zA-Z0-9_.]+$/` — alphanumerics plus underscore and dot only.
  - `password`: `/^(?=.*[A-Za-z])(?=.*\d).+$/` — a **lookahead-based** pattern requiring at least one letter *and* at least one digit somewhere in the string (the `(?=...)` groups check without consuming characters, then `.+` matches the actual content) — a common regex idiom worth recognizing, since it looks more intimidating than what it does.

This is exactly where a uniqueness check would belong, e.g. a custom RHF `validate` function on the `username` field calling back into `registeredUser`.
- `onAction={() => navigate("/")}` sends an already-registering user back to `/` (Login) — consistent with `/` being `AuthLayout`'s guarded path (§7.2), unlike `Register` itself which isn't reciprocally guarded.

| | `Products.jsx` | `Users.jsx` |
|---|---|---|
| Endpoint | `axiosInstance.get("/products")` | `axiosInstance.get("/users")` |
| State names | `products` | `usersData` |
| Card rendered | `ProductCard` | `UserCard` |

### 11.2 The Shared Pattern, Explained Once

- `isLoading` starts `true` (not `false`) — meaning the loading UI is what renders on the *very first* paint, before `useEffect` has even had a chance to fire. Starting `false` and only flipping to `true` inside `getProductsData`/`getUsersData` would produce a one-frame flash of the "0 items" empty state before the fetch kicks in — starting `true` avoids that.
- `try / catch / finally` — `finally` guarantees `setIsLoading(false)` runs whether the request **succeeds or fails**, which is what makes the three-way `isLoading ? ... : data.length === 0 ? ... : ...` render logic reliable: a failed request still exits the loading state (falling through to the "No records found" branch, since `products`/`usersData` stays `[]` on error) instead of leaving the UI stuck showing a permanent loading spinner.
- `useEffect(() => { getProductsData(); }, [])` — empty dependency array, fetch-once-on-mount, exactly the same pattern flagged in Module 1's `App.jsx` (and the same fix that app already applied over its own earlier draft that had `[toggle]` as a dependency).

### 11.3 Worth Reconsidering — Duplicated Fetch Logic

- These two files are close to line-for-line identical except for the endpoint, variable names, and the card component. This is a natural candidate for extraction into a shared custom hook, something like:

  ```js
  function useFetchList(endpoint) {
    const [data, setData] = useState([]);
    const [isLoading, setIsLoading] = useState(true);

    useEffect(() => {
      let cancelled = false;
      (async () => {
        try {
          setIsLoading(true);
          const response = await axiosInstance.get(endpoint);
          if (!cancelled) setData(response.data);
        } catch (error) {
          console.error(`Error fetching ${endpoint}:`, error);
        } finally {
          if (!cancelled) setIsLoading(false);
        }
      })();
      return () => { cancelled = true; };
    }, [endpoint]);

    return { data, isLoading };
  }
  ```

  Not a bug — the current duplication works correctly exactly as written — but it's the same "extract the repeated part into a hook" instinct that produced `useAuth` (§5) out of what would otherwise be duplicated form/context/navigation wiring in both `Login` and `Register`.


- `const inStock = (rating?.count ?? 0) > 0;` — two defensive operators stacked together, worth naming individually since they solve different problems:
  - `?.` (**optional chaining**) — if `rating` itself is `null`/`undefined`, `rating?.count` short-circuits to `undefined` instead of throwing a "cannot read property `count` of undefined" error.
  - `??` (**nullish coalescing**) — `undefined ?? 0` falls back to `0` specifically when the left side is `null`/`undefined` (unlike `||`, which would *also* fall back on `0` itself, `""`, or `false` — values that are legitimately "falsy" but not actually missing). Since a rating count of `0` is a perfectly valid real value, `??` is the correct choice here over `||`: `0 || 0` would coincidentally give the same result, but `someRealNonZeroValue ?? 0` and `someRealNonZeroValue || 0` only behave identically because nothing here can legitimately be `0` *and* falsy-but-not-missing at the same time — worth knowing `??` is the deliberately correct tool regardless.
  - The same pattern repeats for `rating?.rate ?? "—"` and `rating?.count ?? 0` in the JSX below — displaying an em dash instead of crashing or showing `"undefined / 5"` when a product genuinely has no rating data from the API.
- `inStock` is really "**has been rated**" (`rating.count > 0`), not literal stock/inventory availability — the Fake Store API this hits doesn't expose real inventory counts, so `rating.count` is being reused as a stand-in signal, labeled accordingly as `"Unreviewed"` rather than `"Out of stock"` in the false branch — a reasonable, honest choice of label given what data is actually available.

If it had been defined *inside* `UserCard`'s function body instead, React would treat it as a brand-new component type on every single render of `UserCard`, discarding and remounting its DOM every time — this code avoids that pitfall by keeping `Segment`'s definition at the top level of the file, outside `UserCard` itself, so it's created once.
- `user.name.firstname.charAt(0)` — no optional chaining here, unlike `ProductCard`'s `rating?.count`. This assumes `user.name` and both name fields are **always** present on every object the Fake Store API's `/users` endpoint returns — a reasonable assumption for a known, stable fake API, but worth noting as a spot where the defensive `?.` pattern from `ProductCard` (§12.1) *isn't* applied, so this component would throw if a user object were ever missing that nested shape.
- `StatusBadge label="Active"` is **hardcoded** — every single user card always shows "Active," regardless of any real data (there's no `user.active` or similar field being read). Unlike `ProductCard`'s `StatusBadge`, which is genuinely computed from `inStock`, this one is decorative/static for now. Not wrong, just worth knowing it isn't reflecting anything from the API.

## 14. `main.jsx` & `App.jsx` — Entry Point, and a Dead File

### 14.1 `main.jsx`

```jsx
import { createRoot } from "react-dom/client";
import "./index.css";
import AppRoutes from "./routes/AppRoutes.jsx";
import { AuthProvider } from "./context/AuthContext.jsx";
import { ToastContainer } from "react-toastify";

createRoot(document.getElementById("root")).render(
  <AuthProvider>
    <AppRoutes />
    <ToastContainer />
  </AuthProvider>
);
```

- `AuthProvider` wraps `AppRoutes`, so `useContext(Auth)` works anywhere inside the router tree — same "must be inside the Provider" requirement as every Context example so far.
- **No `<BrowserRouter>` here**, unlike Module 2's `main.jsx` — and that's correct, not a missing piece. In data-router mode, `createBrowserRouter` (called inside `AppRoutes.jsx`) already creates the router instance itself; `<RouterProvider>` is what consumes it. The separate `<BrowserRouter>` **component** is specific to the declarative mode from Module 2 and isn't used (or needed) here at all.
- `<ToastContainer />` — react-toastify's single portal component, rendered once here as a **sibling** to `<AppRoutes />`, not nested inside it. This is exactly why `toast.success(...)`/`toast.error(...)` calls from `useAuth.jsx`, deep inside the auth flow, can pop up correctly — the `ToastContainer` renders a container for react-toastify's notifications regardless of which route is currently active, since it lives outside the swappable route tree entirely.

### 14.2 `App.jsx` — Uploaded, but Dead Code

```jsx
import React from 'react'

const App = () => {
  return (
    <div>
      <h1 className='text-white text-5xl'>Hello, World!</h1>
    </div>
  )
}

export default App
```

- **Worth flagging explicitly:** `main.jsx` never imports or renders `App` at all — it renders `AppRoutes` directly. This file is very likely a **leftover from Vite's default scaffold** (every fresh `npm create vite` React project starts with exactly this kind of placeholder `App.jsx`) that never got deleted once routing took over as the actual entry point. It's not wired into the app in any way right now — safe to delete, unless there's a plan to reintroduce it as an actual shell component later.

## Quick Summary

```
AUTH STATE (AuthContext.jsx)
- Context holds ONLY raw state + setters (registeredUser, loggedInUser, setters)
  — no login()/register() functions live in the Provider itself.
- Initial state read from localStorage via JSON.parse(getItem(...)) || fallback
  — JSON.parse(null) → null is a real, intentional coercion, not a bug.
- registerFormSubmit has NO duplicate-username check (same gap class as
  Module 1's addToCart, but here it's actually reachable through the UI).

AUTH LOGIC (useAuth.jsx)
- One custom hook = useForm + useContext(Auth) + useNavigate, bundled.
- loginFormSubmit: linear .find() over registeredUser for a matching
  username+password pair. Client-only fake auth — no real backend.
- Both submit handlers do the "update state + mirror to localStorage +
  toast + navigate" bundle together, every time.

ROUTE GUARDS (AuthLayout.jsx / ProtectedRoutes.jsx)
- Mirror images: AuthLayout keeps LOGGED-IN users OUT of "/", ProtectedRoutes
  keeps LOGGED-OUT users OUT of "/main".
- Both use <Navigate to="..."/> — DECLARATIVE redirect (rendered, not called)
  — vs useNavigate()'s IMPERATIVE navigate("...") used inside useAuth.
- Gap: /register sits OUTSIDE AuthLayout's guard — logged-in users can
  still reach and resubmit it.

DATA ROUTER (AppRoutes.jsx) — different API than Module 2
- createBrowserRouter([...route objects...]) + <RouterProvider router={router}/>
  REPLACES <BrowserRouter><Routes><Route> JSX from Module 2.
- Nesting = `children` arrays instead of nested <Route> tags;
  path: "" means "exact match to the parent," same idea as Module 2's
  relative child paths.
- Official guidance: create the router ONCE, outside the component tree
  — this file creates it inside AppRoutes' function body instead.

NAVLINK — THE MODULE 2 FIX, APPLIED (NavItem.jsx)
- className AND children both passed as FUNCTIONS of { isActive }
  — this is what Module 2's Navbar was missing entirely.
- `end` prop on the "/main" link only — prevents it from staying "active"
  on every sub-route (/main/products, /main/users), since NavLink matches
  by default on any URL that STARTS WITH `to`.

DATA FETCHING (Products.jsx / Users.jsx)
- Identical pattern: isLoading starts true (avoids an empty-state flash),
  try/catch/finally guarantees isLoading resolves even on failure.
- Near-duplicate across both files — good candidate for a shared hook.

MISC
- rating?.count ?? 0 — optional chaining (?.) guards against a missing
  object; nullish coalescing (??) supplies a default ONLY for null/undefined,
  correctly preserving a real `0` (unlike `||`, which would too, but for
  the wrong reason — || also treats "", false as needing a fallback).
- App.jsx is uploaded but completely unused — main.jsx renders AppRoutes
  directly, not App. Vite scaffold leftover.
```
