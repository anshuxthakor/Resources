# TypeScript 03 — Typing a Real React App (Fetching & Rendering Products)

## 1. The Shift From `typescript-02`

Note 02 was about typing a **single standalone function** (`sum`). This one is a full **Vite + React + TypeScript** project — so the same core idea (types describing shapes of data) now spreads across *config files*, *interfaces*, *generics on hooks*, and *typed component props*. Five files, one pipeline:

```
tsconfig.json  →  points at two sub-configs (app code vs. node/build tooling)
   ↓
types.ts       →  defines the SHAPE of a "Product"
   ↓
App.tsx        →  fetches products, stores them typed as Product[]
   ↓
ProductCard.tsx → receives one typed Product as a prop, renders it
   ↓
main.tsx       →  mounts App into the real DOM
```

---

## 2. `tsconfig.json` — The "Solution" Config

```json
{
  "files": [],
  "references": [
    { "path": "./tsconfig.app.json" },
    { "path": "./tsconfig.node.json" }
  ]
}
```

- `"files": []` — this root config **contains no settings of its own** and compiles nothing directly.
- `"references"` — it just points at two **separate** configs. This is TypeScript's **project references** feature: instead of one config trying to handle everything, you split by *environment*.

### Why split into two?

| | `tsconfig.app.json` | `tsconfig.node.json` |
|---|---|---|
| **Governs** | Your actual app code (`src/`, React components) | Build tooling that runs in Node (`vite.config.ts`) |
| **`lib`** | `["ES2023", "DOM"]` — needs DOM types (`document`, `window`) | `["ES2023"]` only — no DOM, it never runs in a browser |
| **`types`** | `["vite/client"]` — Vite's client-side ambient types (e.g. `import.meta.env`) | `["node"]` — Node's global types (`process`, `__dirname`, etc.) |
| **`module`** | `"esnext"` | `"nodenext"` — matches how Node actually resolves modules |
| **`jsx`** | `"react-jsx"` — understands `.tsx` JSX syntax | *(absent — this config never sees JSX)* |
| **`include`** | `["src"]` | `["vite.config.ts"]` |

**The reasoning:** your React components and your Vite config file run in two *completely different* environments (browser-like vs. Node.js) with different global objects available. Giving them separate `lib`/`types` means TypeScript won't let your component code accidentally use a Node-only global (like `process`), or your config file accidentally use a browser-only one (like `document`) — each config only knows about the globals that actually exist where that code runs.

### Shared linting flags (both configs)

```json
"noUnusedLocals": true,
"noUnusedParameters": true,
"erasableSyntaxOnly": true,
"noFallthroughCasesInSwitch": true
```

- `noUnusedLocals` / `noUnusedParameters` — errors on variables/params you declare but never use (catches dead code and typos).
- `erasableSyntaxOnly` — restricts you to TS syntax that disappears cleanly on compile (ties back to the **type erasure** idea from note 02 — no TS-only runtime features like `enum` that would need actual generated JS logic).
- `noFallthroughCasesInSwitch` — errors if a `switch` case is missing a `break`/`return` and silently falls into the next case.

### Bundler-mode flags (in `tsconfig.app.json`)

```json
"moduleResolution": "bundler",
"allowImportingTsExtensions": true,
"verbatimModuleSyntax": true,
"noEmit": true,
```

- `"noEmit": true` — TypeScript here is used **only as a checker**, not a compiler. Vite (via esbuild) does the actual `.tsx` → `.js` transformation; `tsc` just watches over your shoulder for type errors.
- `"verbatimModuleSyntax": true` — this is *why* your imports write `import type { Product }` instead of plain `import { Product }` — see §4 below.

## 3. `types.ts` — Describing the Data's Shape

```ts
export interface Product {
  id: number;
  title: string;
  category: string;
  image: string;
  price: number;
  description: string;
  rating: {
    rate: number;
    count: number;
  };
}
```

- `interface` (vs. the `type` alias used for `UserObj` back in note 02) — for describing **object shapes**, `interface` and `type` are near-interchangeable; `interface` is the more idiomatic choice specifically for object/props shapes like this one, and — unlike `type` — it can later be *extended* by another interface or *re-opened* to add more fields.
- `rating` is a **nested object type**, written inline rather than pulled out as its own named interface — fine here since it's small and only used in one place.
- The commented-out list above it (`// category; // description; ...`) looks like scratch notes listing the raw field names from the API response before shaping them into the typed interface below — a rough draft kept as a comment.

### `ApiResponseProduct` — currently unused, and worth flagging

```ts
export interface ApiResponseProduct {
  data?: [];
  total: number;
  skip: number;
}
```

- This interface isn't imported or used anywhere in `App.tsx` yet — likely scaffolding for a future response wrapper.
- One thing to watch when you do wire it up: `data?: []` doesn't mean *"an optional array of products"* — `[]` as a **type** means "an empty tuple," so TypeScript would only accept an array with **zero elements** for that field. What you'd actually want is `data?: Product[]` (optional array *of* `Product`).

## 4. `import type` — Why "Verbatim Module Syntax" Forces This

```ts
import type { Product } from "./types";
```

- `verbatimModuleSyntax: true` (from §2) requires you to be explicit about **which imports are types vs. real values**, using `import type` for the former.
- **Why it matters:** `Product` is an interface — it exists purely for the compiler and is fully erased at compile time (same erasure idea as note 02's `: number[]`). If TypeScript emitted a normal `import { Product } from "./types"` into the compiled JS, that line would try to import something that **doesn't exist at runtime** — `types.ts` compiles down to an essentially empty file, since interfaces vanish entirely. `import type` tells the compiler "this line is 100% types — strip it out completely," avoiding that broken import.

## 5. `App.tsx` — Fetching, with the Data Typed at the Boundary

```tsx
const [productsData, setProductsData] = useState<Product[]>([]);
```

- `useState` is a **generic function** — `<Product[]>` is the type argument, telling TypeScript exactly what kind of data this piece of state will ever hold.
- Without it, TypeScript would infer the type from the initial value `[]` alone, which would come out as `never[]` (an array that can never actually hold anything) — the explicit `<Product[]>` overrides that inference and says "this starts empty, but will hold `Product` objects."

```tsx
let getData = async () => {
  let res = await axios.get("https://fakestoreapi.com/products");
  console.log(res);
  setProductsData(res.data);
};

useEffect(() => {
  getData();
}, []);
```

- `axios.get(...)` here isn't given a type argument (it *can* be written `axios.get<Product[]>(...)` for a fully-typed response), so `res.data` comes back as `any` — TypeScript trusts you and won't flag a mismatch even if the API's actual shape drifted from your `Product` interface. `setProductsData(res.data)` still works because `any` is assignable to anything.
- `useEffect(..., [])` — empty dependency array means `getData()` runs exactly **once**, right after the component first mounts (the classic "fetch on load" pattern).

```tsx
{productsData.map((val) => (
  <ProductCard key={val.id} product={val} />
))}
```

- Because `productsData` is typed as `Product[]`, TypeScript already knows `val` inside `.map()` is a full `Product` — you get autocomplete on `val.id`, `val.title`, etc. with no extra annotation needed here; the typing done once at `useState<Product[]>` carries through everywhere the array is used.
- `key={val.id}` — React's list-rendering requirement, using the product's own `id` rather than the array index (a stabler key if the list ever gets reordered/filtered).

## 6. `ProductCard.tsx` — Typing Props Inline

```tsx
const ProductCard = ({ product }: { product: Product }) => {
```

- This destructures `product` straight out of the props object **and** types the whole props object inline: `{ product: Product }` — a shorthand alternative to writing a separate named type/interface like `ProductCardProps` first. Fine for a component with one prop; once a component takes several props, pulling that shape out into its own named `interface` (the way `types.ts` does for `Product`) keeps the component's signature line readable.
- Everywhere inside the component — `product.image`, `product.title`, `product.category`, `product.description`, `product.price` — is now fully typed and autocompleted, flowing all the way from the original `Product` interface through `App.tsx`'s state, through the `.map()`, into this component's prop.

## 7. `main.tsx` — The Non-Null Assertion

```tsx
createRoot(document.getElementById("root")!).render(<App />);
```

- `document.getElementById(...)` normally returns `HTMLElement | null` — TypeScript can't know for certain that an element with id `"root"` actually exists in the HTML.
- The `!` right after the call is the **non-null assertion operator**: it tells TypeScript *"trust me, this will never be null — stop making me handle that case."* It's a compile-time-only annotation (erased on compile, same family as note 02's erasure discussion) and does **no actual runtime check** — if `#root` genuinely were missing from `index.html`, this would still crash at runtime with a real error; `!` just silences the *type* error, not the real risk.

## 8. Quick Summary

```
tsconfig.json          → root "solution" file, delegates to two sub-configs
tsconfig.app.json       → browser/React code: DOM lib, vite/client types, jsx: react-jsx
tsconfig.node.json      → Node-side tooling (vite.config.ts): node types, nodenext module

interface Product {...}       → single source of truth for "what a product looks like"
import type { Product }       → required by verbatimModuleSyntax — type-only imports
                                  get fully erased, avoiding a broken runtime import

useState<Product[]>([])       → generic: pins down state's type instead of inferring never[]
axios.get(url)                → untyped here → res.data is `any`, no compile-time safety
({ product }: { product: Product }) => ...   → inline prop typing for a single-prop component

document.getElementById("root")!   → non-null assertion: silences the null-check
                                       at compile time, does NOT check at runtime
```
