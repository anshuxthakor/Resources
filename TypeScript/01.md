# TypeScript 01 — Types, Arrays, Tuples, Enums & Unions

This is the first module in a new series — moving from React/JS into **TypeScript**, starting with the fundamentals: type annotation vs inference, primitive types, arrays, tuples, enums, union types, and literal types. Based on your `index.ts` source and its compiled `index.js` output — a useful pairing, since seeing what TypeScript actually *compiles down to* makes clear which parts of TS are compile-time-only checks versus real runtime behavior.

---

## 1. Type Inference vs. Type Annotation

```ts
let a: string = "hello";
a = "pol";
// a = "bye";
```

- **Annotation**: `: string` is you **explicitly telling** TypeScript what type a variable must hold.
- **Inference**: if you'd written `let a = "hello";` (no `: string`), TypeScript would have **inferred** the type as `string` on its own, just from the assigned value — you don't always need to write annotations for TypeScript to type-check a variable correctly.
- Once a variable's type is locked in (whether by annotation or inference), TypeScript enforces it going forward: `a = "pol"` is fine (still a string), but `a = 90` would be a compile-time **type error** — attempting to assign a `number` to a variable typed `string`.

### The Critical Insight: Compiling to `index.js`

```js
// index.js — the compiled output
Object.defineProperty(exports, "__esModule", { value: true });
```

- **TypeScript's type annotations don't exist in JavaScript at all.** Comparing `index.ts` to its compiled `index.js`, notice that every `: string`, `: number`, `: boolean` annotation is **completely stripped away** during compilation — the `.js` output has zero traces of any type information.
- This is the single most important fact to internalize about TypeScript: **types are a compile-time-only tool.** They exist purely to catch mistakes *while you're writing code* (in your editor, and during the build/compile step) — by the time your code actually runs in the browser or Node, it's plain JavaScript, and none of the type-checking machinery is present or running anymore. TypeScript doesn't add any runtime type-checking overhead to your app; it's entirely a development-time safety net.

## 2. Primitive Data Types

```ts
let val: string = "Shubham";
let val2: boolean = true;
let b: number = 90;
let h: undefined = undefined;
let g: bigint = 79697678n;
let y: symbol = Symbol("hello");
```

These map directly onto JavaScript's own primitive types, just with an explicit type annotation attached:

| Type | Example | Notes |
|---|---|---|
| `string` | `"Shubham"` | Text |
| `boolean` | `true` | `true`/`false` only |
| `number` | `90` | TypeScript, like JS, has **one** numeric type — no separate `int`/`float`/`double` |
| `undefined` | `undefined` | The absence of an assigned value |
| `bigint` | `79697678n` | For integers beyond `number`'s safe range — note the trailing `n` |
| `symbol` | `Symbol("hello")` | Unique, immutable identifiers |

### Two Special TypeScript-Only Types (Commented Out in Your Code, Worth Explaining)

```ts
// let a: unknown = "faizal";
// console.log(a.toUpperCase());   // <- this line would error

// let y: never;
```

- **`unknown`**: (cite index="121-1">TypeScript also has a special type, any, that you can use whenever you don't want a particular value to cause typechecking errors</cite> — but `unknown` is the **safer sibling** of `any`. A variable typed `unknown` can hold *any* value, just like `any` — but unlike `any`, TypeScript **won't let you call methods on it or use it** until you first **narrow** its type (e.g., via a type check or type assertion). This is exactly why `a.toUpperCase()` is commented out here: calling `.toUpperCase()` directly on an `unknown`-typed variable is a compile error, because TypeScript can't guarantee `a` is actually a string at that point — even though the assigned value happens to be one. You'd need something like `(a as string).toUpperCase()` (a type assertion) to use it safely.
- **`never`**: represents a value that **can never actually occur** — typically used for functions that always throw an error, or infinite loops, or in exhaustiveness checks (making sure every possible case of a union has been handled). A bare `let y: never;` with no value is unusual outside of specific patterns — this is likely included here purely to demonstrate the type exists, not as a practical usage example.

## 3. Arrays — Typed Collections

```ts
let arr: number[] = [
  5, 6, 7, 8, 9, 0, 67, 8, 9, 0, 6, 5, 43, 2, 3, 4, 5, 6, 7, 8, 9, 0, 87, 6, 5, 4, 3,
];

let arr1: string[] = ["jio", "pol", "john"];

let arrBol: boolean[] = [true, false, true, true, true];
```

- The `Type[]` syntax declares an array where **every element must be the same type**. `number[]` means "an array containing only numbers" — trying to push a string into `arr` later would be a compile-time error.
- This is the same underlying JS array from all your earlier React notes — TypeScript just adds a **guarantee, enforced by the compiler**, about what can go inside it, catching mistakes (like accidentally mixing a string into a numbers-only array) before the code ever runs.

### Compiled Output — Arrays Are "Just Arrays" at Runtime

```js
// index.js
let arr = [5, 6, 7, 8, 9, 0, 67, /* ... */];
let arr1 = ["jio", "pol", "john"];
let arrBol = [true, false, true, true, true];
```

- Exactly as expected from Section 1: the `: number[]`, `: string[]`, `: boolean[]` annotations vanish entirely in the compiled JS. At runtime, these are indistinguishable from plain JavaScript arrays — TypeScript's array typing is a pre-runtime safety check only.

## 4. Tuples — Fixed-Length, Mixed-Type Arrays

```ts
let arr2: [number, number, string, boolean] = [56, 78, "pol", true];
```

- (cite index="120-1">A tuple in TypeScript is a special type of array that has a fixed number of elements, where each element can have a different type. Tuples ensure that the order and types of values remain consistent.</cite>
- **This is the key difference from a regular typed array** (Section 3): `number[]` means *any number* of elements, *all* the same type. A tuple `[number, number, string, boolean]` means **exactly 4 elements**, in **exactly this order**, each with its **own specific type**: position 0 must be a `number`, position 1 must be a `number`, position 2 must be a `string`, position 3 must be a `boolean` — no more, no fewer, and not reorderable.
- (cite index="120-1">Tuples can also have optional elements — e.g. `let person: [string, number, boolean?] = ["Bob", 30];`</cite> and (cite index="120-1">can be marked readonly to prevent modifying tuple values after creation</cite> — neither is used in this example, but both are common tuple features worth knowing.
- **Why use a tuple instead of just typing it loosely?** Tuples are ideal for representing a small, fixed, meaningfully-ordered group of values — e.g. an `[x, y]` coordinate pair, or a `[key, value]` entry — where the position of each element carries specific meaning, unlike a homogenous array where every element is interchangeable.

### Compiled Output — Tuples Are Just Arrays at Runtime Too

```js
let arr2 = [56, 78, "pol", true];
```

- Again — no trace of the tuple's positional type constraints in the compiled JS. **Tuples are a purely TypeScript-level concept**; at runtime, `arr2` is a completely ordinary JavaScript array with no special "tuple-ness" to it. Nothing stops plain JS code from pushing a 5th element onto it at runtime — the tuple's fixed-length, fixed-type guarantee is enforced *only* by the TypeScript compiler, never by the JavaScript engine.

## 5. `data: any[]` — An Array of Loosely-Typed Objects

```ts
let data: any[] = [{ name: "pol" }, { name: "pol" }, { name: "pol" }];
```

- `any` is TypeScript's **type-checking escape hatch** — (cite index="121-1">when a value is of type any, you can access any properties of it, call it like a function, assign it to or from a value of any type, or pretty much anything else that's syntactically legal.</cite>
- `any[]` means "an array where each element can be **literally anything**, with no type checking applied to it at all." This is notably looser than declaring, say, `{ name: string }[]` (an array of objects that must each have a `name` property typed as a string) — with `any[]`, TypeScript wouldn't catch it if one of these objects were accidentally missing `name`, or had `name` set to a number instead of a string.
- **Worth flagging as a gotcha:** (cite index="121-1">the any type is useful when you don't want to write out a long type just to convince TypeScript that a particular line of code is okay — but you usually want to avoid this, because any isn't type-checked.</cite> Using `any` essentially opts a piece of code **out** of TypeScript's core benefit. A more precise version here would define a proper shape, e.g. `let data: { name: string }[] = [...]`, which this specific line doesn't do — likely fine for a quick learning example, but worth knowing this is the "loose" way to type this data, not the ideal one for production code.

## 6. Enums — Named Sets of Constants

```ts
enum Role {
  ADMIN,
  SUP_ADMIN,
  USER,
}
let role: Role = Role.USER;
```

- (cite index="121-1">Enums are a feature added to JavaScript by TypeScript which allows for describing a value which could be one of a set of possible named constants. Unlike most TypeScript features, this is not a type-level addition to JavaScript but something added to the language and runtime.</cite> This last point is genuinely important — **enums are the one feature in this module that is NOT purely compile-time-erased**, unlike everything else covered so far. Confirm this directly in the compiled output below.
- This is a **numeric enum** (no explicit values assigned to each member) — by default, TypeScript auto-assigns incrementing numbers starting from `0`: `ADMIN = 0`, `SUP_ADMIN = 1`, `USER = 2`.
- `Role.USER` accesses the enum member by name, and `let role: Role = Role.USER` types `role` as belonging to the `Role` enum specifically — meaning `role` can only ever be assigned one of `Role.ADMIN`, `Role.SUP_ADMIN`, or `Role.USER`, not an arbitrary number.

### Compiled Output — Enums *Do* Generate Real Runtime Code

```js
var Role;
(function (Role) {
    Role[Role["ADMIN"] = 0] = "ADMIN";
    Role[Role["SUP_ADMIN"] = 1] = "SUP_ADMIN";
    Role[Role["USER"] = 2] = "USER";
})(Role || (Role = {}));
let role = Role.USER;
```

- Unlike every other type annotation in this module (all stripped away entirely), **the `enum` declaration itself compiles into real, executable JavaScript** — an immediately-invoked function expression (IIFE) that builds an object with a clever **double mapping**: `Role["ADMIN"] = 0` (name → number) **and** `Role[0] = "ADMIN"` (number → name), assigned via the chained `Role[Role["ADMIN"] = 0] = "ADMIN"` expression.
- This double mapping is what lets you do both `Role.ADMIN` (→ `0`) **and** `Role[0]` (→ `"ADMIN"`) at runtime — a genuinely useful, TypeScript-specific runtime feature, not just a compile-time type check. This is exactly why enums are called out as an exception to the "types vanish at compile time" rule from Section 1 — enums are as much a runtime language feature as a type-system feature.

## 7. Union Types — "This OR That"

```ts
let yolo: string | number = "rahul";
yolo = 90;
```

- The `|` (pipe) symbol creates a **union type** — (cite index="122-1">a special type in which we can assign multiple types to a single variable.</cite>
- `string | number` means `yolo` can legally hold **either** a `string` **or** a `number` at different points — both `"rahul"` (a string) and `90` (a number) are valid assignments to the same variable, without any type error. This is different from `any`: `yolo` still can't be assigned, say, a `boolean` or an object — it's restricted to exactly the two types listed in the union, no more.

### Compiled Output — Unions Are Also Fully Erased

```js
let yolo = "rahul";
yolo = 90;
```

- Consistent with Section 1's core principle: the `string | number` annotation disappears entirely. At runtime, this is just a plain JS variable being reassigned from a string to a number — completely unremarkable, ordinary JavaScript. The union type's entire value is in catching, *at compile time*, any attempt to later assign `yolo` something outside `string | number` (like a boolean) — a mistake plain JavaScript would never catch on its own.

## 8. Literal Types — Restricting to Specific Values

```ts
type Status = "pending" | "success" | "error";
let status: Status = "pending";
```

- This combines two ideas: **type aliases** (`type Status = ...`, giving a reusable name to a type definition) and **string literal types** — where the type isn't just "any string," but **one specific, exact string value**.
- (cite index="121-1">By combining literals into unions, you can express a much more useful concept — functions or variables that only accept a certain set of known values.</cite> `"pending" | "success" | "error"` is a union of **three literal types**, meaning `status` can be assigned `"pending"`, `"success"`, or `"error"` — and **nothing else**. Assigning `status = "loading"` would be a compile-time error, even though `"loading"` is a perfectly valid `string` — it's just not one of the three specific literals this type permits.
- **Why this is genuinely useful, compared to just typing `status: string`:** with a plain `string` type, a typo like `"pendign"` would compile without complaint (it's still a valid string) and only fail at runtime, likely silently, when some comparison against `"pending"` never matches. With the literal-union type `Status`, that same typo is caught immediately at compile time — TypeScript knows the full, exact set of valid values and rejects anything outside it.
- **Enums vs. string-literal unions, a natural comparison:** both `Role` (Section 6) and `Status` (this section) solve a similar underlying problem — restricting a variable to one of a small, known set of options. Enums are a distinct runtime construct (Section 6); a literal-union type like `Status` is a **pure compile-time-only** construct (confirmed below) — no object gets generated for it at all. Which to reach for depends on whether you need an actual runtime value object (favor `enum`) or just a compile-time constraint on which strings are valid (favor a literal union type, often the more lightweight, more commonly recommended modern choice for simple "one of these known strings" cases).

### Compiled Output — Type Aliases and Literal Types Vanish Completely

```js
let status = "pending";
```

- Notice there's **no equivalent at all** in the compiled JS for `type Status = "pending" | "success" | "error";` — not even a stripped-down trace of it, unlike enums. `type` aliases are a **pure TypeScript-level construct**, existing solely to describe shapes/constraints for the compiler; they generate **zero** runtime code, ever. `status` ends up as an entirely ordinary JS variable holding the string `"pending"`.

## 9. Summary Table — What Survives Compilation?

| TypeScript feature | Compiles to real runtime JS? |
|---|---|
| Type annotations (`: string`, `: number[]`, etc.) | ❌ Fully erased |
| Tuples (`[number, string, ...]`) | ❌ Fully erased — becomes a plain array |
| Union types (`string \| number`) | ❌ Fully erased |
| Literal types & `type` aliases (`type Status = "a" \| "b"`) | ❌ Fully erased |
| `unknown` / `never` / `any` | ❌ Fully erased (compile-time checks only) |
| **`enum`** | ✅ **Generates a real runtime object** (the IIFE double-mapping pattern) |

## Quick Summary

```
Core principle: TypeScript types are (mostly) a COMPILE-TIME-ONLY safety net.
  → compare any .ts file to its compiled .js output — nearly everything
    type-related is stripped away entirely

Annotation vs inference:
  let a: string = "x"      → explicit annotation
  let a = "x"                → TypeScript INFERS string on its own

Arrays vs Tuples:
  number[]                        → any number of elements, all the same type
  [number, string, boolean]        → FIXED length, FIXED order, per-position types

any vs unknown:
  any        → opts OUT of type checking entirely (avoid when possible)
  unknown    → holds anything, but you must NARROW it before using it

Union types:            string | number           → "this OR that", nothing else
Literal types:           "pending" | "success"     → one of these EXACT values only
type Status = "a" | "b"                             → reusable named alias for a union

Enums — the ONE exception to "types vanish at compile time":
  enum Role { ADMIN, SUP_ADMIN, USER }
  → compiles into a REAL runtime object with a double name<->number mapping
  → Role.ADMIN === 0   AND   Role[0] === "ADMIN"
```
