# React — `useEffect` Hook

## 1. What is `useEffect`?

**`useEffect`** is a React hook used to run **side effects** in a functional component — code that reaches *outside* the normal render-and-return-JSX flow, such as fetching data from an API, setting timers/intervals, subscribing to events, or manually interacting with the DOM.

<cite index="49-1">The useEffect Hook allows you to declare side effects in functional components. It accepts a setup function and an optional dependencies array, running the setup after the component commits, and running any cleanup before re-runs or before unmounting.</cite>

```js
useEffect(() => {
  // setup / side-effect code
  return () => {
    // optional cleanup code
  };
}, [dependencies]);
```

<cite index="49-1">useEffect takes a setup function (required) which contains your effect's logic and may optionally return a cleanup function, and a dependencies array (optional) listing all reactive values referenced in the setup code — props, state, or variables declared in the component body.</cite>

---

## 2. The Dependency Array — Controlling *When* an Effect Runs

The **second argument** to `useEffect` (the dependency array) is what determines the effect's timing behavior. There are three distinct forms:

| Form | Behavior |
|---|---|
| `useEffect(fn)` — **no array at all** | <cite index="43-1">Without dependencies, the effect runs on mount AND on every single re-render</cite> |
| `useEffect(fn, [])` — **empty array** | <cite index="43-1">The effect is called once, only on mount, and won't run again for subsequent renders unless the component unmounts and remounts</cite> |
| `useEffect(fn, [dep1, dep2])` — **array with values** | <cite index="43-1">The effect runs on mount, and then again on any subsequent render where one or more of the listed dependencies have changed</cite> |

This is the exact mechanism your `App.jsx` code uses:

```js
useEffect(() => {
  console.log("App.jsx Rendering...");
  fetchData();
  console.log(apidata);
}, [toggle]);
```

- `[toggle]` means this effect runs **on mount**, and then **again every time `toggle` changes** — but critically, it does **not** re-run when `count` changes, even though `count` also lives in this same component and also triggers re-renders. This is the core value of the dependency array: it lets you scope an effect to react *only* to the specific pieces of state/props it actually cares about, ignoring unrelated re-renders.

## 3. The Cleanup Function — Mount, Update & Unmount Phases

```js
useEffect(() => {
  // setup — runs on mount / when dependencies change
  return () => {
    // cleanup — runs before the NEXT effect, and on unmount
  };
}, []);
```

<cite index="44-1">The cleanup function runs not only during unmount, but before every re-render with changed dependencies.</cite> This means the cleanup function has **two** distinct jobs, not just one:

1. **Before every re-run of the effect** (i.e., whenever a dependency changes) — React first calls the *previous* cleanup function, then runs the new setup code. <cite index="43-1">During a re-render, React calls the cleanup function to clean up effects from the previous render, before calling the useEffect callback again.</cite>
2. **On unmount** — when the component is removed from the tree entirely, React calls the cleanup function one final time, with no new setup following it.

<cite index="44-1">Your cleanup logic should be "symmetrical" to the setup logic — it should stop or undo whatever the setup did.</cite> This is exactly the pattern in `About.jsx`: the setup starts an interval (`setInterval`), and the cleanup stops that *same* interval (`clearInterval`) — undoing precisely what was started.

> **Development-mode note:** <cite index="44-1">in development, React runs setup and cleanup one extra time immediately after the component mounts</cite> (when `<StrictMode>` is active) — this is intentional, to help surface bugs where cleanup logic is missing or incorrect. It doesn't happen in production builds.

### Mapping to "Mount" / "Unmount" Phase Language

Your notes' comments (`// Mounting Phase`, `// Unmounting Phase`) map directly onto this:

```js
useEffect(() => {
  // Mounting Phase — runs once, since the dependency array is []
  console.log("About.jsx Rendering...");
  const interval = setInterval(() => {
    console.log("Hey I am in About.jsx");
  }, 1000);

  return () => {
    // Unmounting Phase — runs when About.jsx is removed from the tree
    console.log("I am triggered kyuki About.jsx is unmounted.");
    clearInterval(interval);
  };
}, []);
```

- Since the dependency array here is `[]` (empty), the setup code runs **exactly once**, right after `About` first mounts.
- The **only** time the returned cleanup function fires is when `About` **unmounts** — because with an empty dependency array, there's never a "changed dependency" re-run to trigger cleanup early; unmounting is the only remaining trigger.

## 4. Full Code Walkthrough

### 4.1 `App.jsx` — Fetching Data & Conditional Rendering

```jsx
import React, { useEffect, useState } from "react";
import Home from "./components/Home";
import About from "./components/About";
import axios from "axios";

const App = () => {
  const [count, setCount] = useState(0);
  const [toggle, setToggle] = useState(true);
  const [apidata, setApiData] = useState([]);

  let fetchData = async () => {
    try {
      let response = await axios.get('https://fakestoreapi.com/products');
      setApiData(response.data);
    } catch (error) {
      console.error('Error fetching data:', error);
    }
  };
  useEffect(() => {
    console.log("App.jsx Rendering...");
    fetchData();
    console.log(apidata);
  }, [toggle]);

  return (
    <div className="div">
      <h1 className="num">{count}</h1>
      <button className="btn" onClick={() => setCount(count + 1)}>
        Increment
      </button>
      <button className="toggle" onClick={() => setToggle((prev) => !prev)}>
        ✝
      </button>
      {
        toggle ? (
          <Home />
        ) : (
          <About />
        )
      }
    </div>
  );
};

export default App;
```

**Three independent pieces of state:**
- `count` — a simple number, incremented by the "Increment" button.
- `toggle` — a boolean that decides whether `Home` or `About` is rendered.
- `apidata` — holds the array of products fetched from the API.

**The `fetchData` function:**
```js
let fetchData = async () => {
  try {
    let response = await axios.get('https://fakestoreapi.com/products');
    setApiData(response.data);
  } catch (error) {
    console.error('Error fetching data:', error);
  }
};
```
- Uses **Axios** (a promise-based HTTP client) to make a `GET` request to the Fake Store API's products endpoint.
- `async`/`await` is used to pause execution until the request resolves, rather than chaining `.then()`.
- Wrapped in `try/catch` so that a failed request (network error, bad response, etc.) is caught and logged, rather than crashing the component or leaving `apidata` in an inconsistent state.
- On success, `response.data` (the array of product objects) is stored into state via `setApiData`.

**Why `fetchData` is called inside `useEffect`, not directly in the component body:**
- Data fetching is a classic **side effect** — it reaches outside the component to talk to a remote server. If `fetchData()` were called directly in the component body (outside `useEffect`), it would fire on **every single render** (including the ones caused by unrelated state changes like `count` incrementing), triggering a fresh, unnecessary API call each time. Wrapping it in `useEffect` with `[toggle]` as the dependency scopes exactly when re-fetching should happen.

**⚠️ A subtle bug worth flagging — `console.log(apidata)` inside the effect:**
```js
useEffect(() => {
  console.log("App.jsx Rendering...");
  fetchData();
  console.log(apidata);   // <-- logs the OLD value, not the freshly fetched one
}, [toggle]);
```
- `fetchData()` is `async` — calling it does **not** pause execution of the rest of the effect's synchronous code. `setApiData(response.data)` only happens *after* the `await`ed request resolves, which is **after** this effect function has already finished running.
- So `console.log(apidata)` immediately below it logs whatever `apidata` **was** at the start of this render — not the data that was just fetched. You'd need a separate `useEffect` with `[apidata]` as its dependency (or simply move logging into `fetchData` itself, right after `setApiData`) to reliably log the freshly fetched data.
- This is a common beginner trap with `useEffect` + async calls: state setters don't update state *synchronously* within the same function, so code immediately after a `set...` call still sees the pre-update value (the same underlying idea as the state-update timing discussed in your earlier batching notes).

**Why `[toggle]` and not `[]` or no array:**
- `[]` would only fetch data **once**, on the very first mount, and never again — regardless of how many times the user toggles between `Home`/`About`.
- **No array at all** would re-fetch on **every** render — including every single click of "Increment," which has nothing to do with the API data at all. That would be wasteful and could hammer the API unnecessarily.
- `[toggle]` strikes a middle ground: re-fetch specifically when the user switches views — though whether that's the *intended* behavior depends on the app's actual requirements (re-fetching on every toggle isn't obviously necessary here, since the product data itself doesn't depend on which view is showing — this may be worth reconsidering as the app grows, e.g. switching to `[]` if the data only needs to be fetched once).

**Conditional rendering:**
```jsx
{ toggle ? <Home /> : <About /> }
```
- A ternary, rendering `Home` when `toggle` is `true`, `About` otherwise — functionally the same idea as the `{condition && <Component/>}` pattern from earlier notes, just handling **both** branches instead of one branch vs. nothing.
- As covered before, this means whichever component isn't currently active is **fully unmounted** — which is exactly why `About.jsx`'s cleanup-with-interval example (below) is meaningful: switching away from `About` genuinely unmounts it, triggering its cleanup function for real.

### 4.2 `Home.jsx` — No Effect, Just a Render Log

```jsx
import React, { useEffect } from 'react'

const Home = () => {
  console.log("Home.jsx Rendering...")
  return (
    <div>
      <h1 className='file'>Home.jsx</h1>
    </div>
  )
}

export default Home
```

- Note: `useEffect` is **imported but never used** here — a harmless leftover import.
- `console.log("Home.jsx Rendering...")` is placed directly in the component body (**not** inside a `useEffect`), meaning it logs on **every render** of `Home` — including the very first mount and any subsequent re-render, if `Home` ever had reason to re-render while mounted. Since `Home` currently receives no props and has no internal state, in practice this only fires once per mount (whenever `toggle` switches back to `true`).

### 4.3 `About.jsx` — Setup + Cleanup with `setInterval`

```jsx
import React, { use, useEffect } from 'react'

const About = () => {
  useEffect(() => {
    // Mounting Phase
    console.log("About.jsx Rendering...");    
    const interval = setInterval(() => {
      console.log("Hey I am in About.jsx")
    }, 1000);

    // Use when your component leaks some memory 
    // And if you want to track any updates
    return () => {   // Unmounting Phase
      console.log("I am triggered kyuki About.jsx is unmounted.");
      clearInterval(interval);
    };
  }, []);
  return (
    <div>
      <h1 className='file'>About.jsx</h1>
    </div>
  )
}

export default About
```

**Step-by-step lifecycle:**

1. **User clicks the "✝" toggle button** → `toggle` flips to `false` → `App` re-renders → `<About />` mounts for the first time.
2. **`About`'s `useEffect` setup runs** (empty dependency array → runs once, on this mount):
   - Logs `"About.jsx Rendering..."`.
   - Starts a `setInterval` that logs `"Hey I am in About.jsx"` every 1000ms (1 second), repeatedly, **forever, until something stops it**.
3. **While `About` stays mounted**, that interval keeps firing every second in the background — completely independent of any re-renders, since this effect never re-runs (empty dependency array).
4. **User clicks "✝" again** → `toggle` flips back to `true` → `App` re-renders → `<About />` is removed from the tree (unmounted), `<Home />` mounts instead.
5. **React calls `About`'s cleanup function** at this exact moment:
   - Logs `"I am triggered kyuki About.jsx is unmounted."`
   - Calls `clearInterval(interval)` — **stopping the repeating timer**.

**Why the cleanup here is essential (not optional):** without `clearInterval(interval)` in the returned cleanup function, that `setInterval` would **keep running forever in the background**, even after `About` is unmounted and no longer visible — silently logging every second and consuming resources indefinitely. This is a textbook **memory leak** — exactly what the code comment ("use when your component leaks some memory") is pointing at. The interval's closure still holds a reference to its callback, so JavaScript has no way of knowing it's "supposed" to stop just because the component using it visually disappeared; only explicit cleanup (`clearInterval`) actually stops it.

> If you toggled `About` on and off *without* the cleanup function, you'd end up with **multiple overlapping intervals** all running simultaneously — one from each time `About` was mounted — each logging independently, compounding the leak further with every toggle.

## Quick Summary

```
useEffect(setupFn, dependencyArray)

No array          → setup runs on EVERY render
[]                 → setup runs ONCE, on mount only
[dep1, dep2, ...]  → setup runs on mount, and again whenever any listed dependency changes

Cleanup function (the value setupFn optionally returns):
  - runs before the NEXT setup call (when dependencies change)
  - runs on UNMOUNT (final time, no setup follows)
  - should undo/reverse exactly what setup did (clearInterval for setInterval,
    removeEventListener for addEventListener, cancel a subscription, etc.)

Common side effects handled via useEffect:
  - API calls (axios/fetch)       → fetch data after mount / when a dependency changes
  - Timers (setInterval/setTimeout) → MUST be cleared in cleanup, or they leak
  - Event listeners / subscriptions → MUST be removed in cleanup

Gotcha: state setters (setApiData, etc.) don't update state synchronously —
code immediately after a set-call in the same function still sees the OLD value.
```
