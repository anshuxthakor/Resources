# React Memoization — `React.memo`, `useMemo` & `useCallback`

This module is a small, self-contained demo of React's three memoization tools working together: `useMemo` (caching an expensive **calculation**), `useCallback` (caching a **function reference**), and `React.memo` (skipping a **component's own re-render** when its props haven't changed). Where Module 1's `cartItem`/`subtotal` were deliberately recalculated **fresh every render** because they were cheap, this module is about the opposite situation: a calculation expensive enough that recalculating it on every render is itself the problem worth solving.

> A `learn.excalidraw` file was also uploaded alongside this code — checked it, and it contains **only freehand pen strokes** (1,364 `freedraw` elements, no text/diagram elements at all), so there's nothing extractable from it as notes. If it was meant to carry annotations, they didn't save as text in this export.

---

## 1. Architecture Overview

```
main.jsx
  └── App.jsx        (owns: count, users state + the memoized calculation/function)
        ├── Home.jsx    (wrapped in React.memo — expects a `users` prop, but see §5)
        └── About.jsx   (wrapped in React.memo — receives `greet`, calls it directly in render)
```

> Core idea: `React.memo` only helps a **child** skip re-rendering when its **parent** re-renders for unrelated reasons — it does nothing to stop the parent itself from re-rendering, and it only works at all if the props being compared are *referentially* stable between renders. `useMemo` and `useCallback` exist specifically to **produce** that referential stability, for a value and a function respectively.

---

## 2. Three Different Tools, One Family — What Each Actually Memoizes

| | What it caches | Recomputes when | Typical pairing |
|---|---|---|---|
| `useMemo(fn, deps)` | The **return value** of `fn` | Any value in `deps` changes (by reference/value) | Expensive calculations; objects/arrays passed as props to a `memo`-wrapped child |
| `useCallback(fn, deps)` | The **function itself** (its identity) | Any value in `deps` changes | Functions passed as props to a `memo`-wrapped child (event handlers, callbacks) |
| `React.memo(Component)` | The **rendered output** of a component | The component's own **props** change (shallow comparison) — its parent re-rendering alone is *not* enough | Wrapping the child that's receiving the memoized value/function above |

> All three exist to solve the *same underlying problem* from different ends: React by default re-renders a component (and everything below it) whenever its state changes or its parent re-renders, even if nothing that component actually cares about has changed. `useMemo`/`useCallback` keep values and functions **referentially stable** across renders when their inputs haven't changed; `React.memo` is what actually **acts** on that stability by skipping a re-render entirely when props compare equal. None of the three does anything useful without at least one of the others — `React.memo` alone is defeated by a parent re-creating a new function/object prop every render, and `useMemo`/`useCallback` alone (with nothing downstream reading the stable reference) just add bookkeeping overhead for no benefit.

## 3. `App.jsx` — The Full Code

```jsx
import React, { useCallback, useEffect, useMemo, useState } from "react";
import Home from "./components/Home";
import About from "./components/About";

const App = () => {
  console.log("App rendering...");

  const [count, setCount] = useState(0);
  const [users, setUsers] = useState({ name: "raghav", id: 789 });

  let calculation = useMemo(() => {
    console.log("calculation running....");
    let sum = 0;

    for (let i = 0; i < 100000000; i++) {
      sum += i;
    }
    return sum;
  }, [users]);

  let greet = useCallback(() => {
    console.log("good evening...");
  }, []);

  return (
    <div>
      <h1>Memoization</h1>
      <h2>Count is {count}</h2>
      <h2>NAme is {users.name}</h2>
      <h2>My calculation is {calculation}</h2>
      <button onClick={() => setUsers({ ...users, name: "Ranjeet" })}>
        Change name{" "}
      </button>
      <button onClick={() => setCount(count + 1)}>Increment</button>
      <Home greet={greet} />
      <About greet={greet} />
    </div>
  );
};

export default App;
```

### 3.1 Two Independent Pieces of State

- `count` — bumped by the **Increment** button. Nothing else in the component reads or derives from `count`.
- `users` — an object (`{ name, id }`), replaced by the **Change name** button via `setUsers({ ...users, name: "Ranjeet" })`. Same spread-to-create-a-new-object rule from Module 1's `addToCart`/`updateQty` — this deliberately produces a **new object reference** every click, even though `id` never actually changes.
- These two pieces of state are intentionally **unrelated** to each other — that separation is what makes the rest of the demo work: clicking one button should be able to leave the other's derived work untouched.

### 3.2 `useMemo` — Caching an Expensive Calculation

```js
let calculation = useMemo(() => {
  console.log("calculation running....");
  let sum = 0;
  for (let i = 0; i < 100000000; i++) {
    sum += i;
  }
  return sum;
}, [users]);
```

- The callback sums integers up to 100 million — a genuinely slow, **synchronous, blocking** loop (this runs on the main thread; `useMemo` does not make it asynchronous or non-blocking, it only controls *how often* it runs).
- `[users]` as the dependency array means: only re-run this loop when the `users` reference changes. Without `useMemo`, this loop would re-run on **every single render** of `App` — including every `count` increment, which has nothing to do with `users` at all.
- **This is the direct opposite instinct from Module 1's derived state** (`cartItem = cart.find(...)`, `subtotal = cart.reduce(...)`), and it's worth being explicit about *why* the two modules reach opposite conclusions: Module 1's derivations were cheap (an array `.find()`/`.reduce()` over a handful of cart items), so recomputing them fresh every render cost nothing and avoided any risk of stale data. This loop is the case `useMemo`'s own documentation calls out explicitly as worth optimizing for — a calculation "noticeably slow" whose dependencies "rarely change." Caching a cheap derivation would be pointless overhead; *not* caching an expensive one is what actually costs something here.

### 3.3 `useCallback` — Caching a Stable Function Reference

```js
let greet = useCallback(() => {
  console.log("good evening...");
}, []);
```

- Every time a component function runs, any `function () {...}` written inside it is a **brand-new function object**, even if the code inside looks identical to the previous render's version — this is the same "new reference every time" concern as object/array creation, just applied to functions specifically.
- `useCallback(fn, [])` with an **empty** dependency array means `greet` is created exactly **once**, on `App`'s first render, and the *exact same function reference* is returned on every subsequent render — never recreated, since nothing in the (empty) dependency list can ever change.
- This matters specifically because `greet` is passed down as a **prop** to two components wrapped in `React.memo` (`Home` and `About`, §4–§5). `React.memo`'s shallow prop comparison checks `Object.is(prevProps.greet, nextProps.greet)` — for functions, that's a reference check. Without `useCallback`, `greet` would be a new function reference on every `App` render, and `Object.is` would report "different" every time, defeating `React.memo` on both children completely regardless of anything else being memoized.

### 3.4 Tracing Both Buttons Through a Render

| Click | `count` | `users` | `calculation` loop re-runs? | `greet` reference changes? | `Home`/`About` re-render? |
|---|---|---|---|---|---|
| **Increment** | changes | unchanged (same reference) | **No** — dependency `[users]` unchanged | No — dependency `[]` never changes | **No**, if their props are otherwise stable (see §4–§5 for why that's *not* quite what happens here) |
| **Change name** | unchanged | changes (new object reference) | **Yes** — dependency `[users]` changed, loop blocks the main thread again | No — dependency `[]` never changes | Same as above |

- `console.log("App rendering...")` fires on **every** click of either button — `React.memo` and `useMemo`/`useCallback` never prevent a component from re-rendering due to **its own** state changes; they only ever help *children* skip re-rendering due to an *unrelated* parent re-render. `App` itself has no memoization applied to it (nor could it meaningfully be given one, since it's the top of this tree) and re-renders on every `setCount`/`setUsers` call, exactly as expected.

## 4. `About.jsx` — `React.memo`, and a Side Effect Living in the Render Body

```jsx
import React from "react";

let a = 10;

const About = ({ greet }) => {
  greet();
  console.log("about rendering...");
  return (
    <div>
      <h1>about this side..</h1>
    </div>
  );
};

export default React.memo(About);
```

### 4.1 `export default React.memo(About)`

- `React.memo` wraps `About` and returns a **new memoized component** — official React docs describe this as: the memoized version "will usually not be re-rendered when its parent component is re-rendered as long as its props have not changed," while also noting explicitly that memoization is "a performance optimization, not a guarantee" — React is allowed to re-render a memoized component anyway in some circumstances, so it shouldn't be relied on as a correctness mechanism, only a performance one.
- The comparison `React.memo` performs by default is **shallow** — for `About`, its only prop is `greet`, so the entire check comes down to whether the `greet` function reference is the same as last render. Because `greet` comes from `useCallback(..., [])` in `App` (§3.3), that reference genuinely never changes — so `About`, in isolation, has everything it needs to skip re-rendering on an Increment click.

### 4.2 Bug/Gotcha Worth Calling Out Explicitly: `greet()` Called Directly in the Render Body

```jsx
const About = ({ greet }) => {
  greet();
  console.log("about rendering...");
  ...
```

- `greet()` is invoked **unconditionally, as part of rendering** — not inside a click handler, not inside a `useEffect`. This means every time `About`'s function body actually runs (which, thanks to `React.memo`, should be limited to mount plus any render where `greet` itself changes — here, effectively just the initial mount), it fires a side effect (a `console.log`, in this harmless case) as a byproduct of rendering.
- This is the same category of concern as your earlier `useEffect` notes: **rendering is supposed to be a pure function of props and state** — calling an arbitrary function during render (rather than in response to an event, or inside an effect) breaks that purity. It happens to be harmless here because `greet` only logs a string, but the *pattern* — "call this function while rendering" — is worth flagging as something to avoid generally, because it doesn't stay harmless once the called function does anything with real side effects (a network call, a state update, a subscription). The fix, if `greet()` genuinely needs to run whenever `About` mounts/updates, is `useEffect(() => { greet(); }, [greet])`, not a bare call in the component body.

### 4.3 `let a = 10;` — Unused Module-Scope Variable

- Declared once at the top of the file, outside the `About` component, and never referenced anywhere afterward. Almost certainly leftover scratch code from experimenting (perhaps testing whether reassigning a module-level variable would trigger a re-render, which it wouldn't — plain variables outside React state don't cause renders no matter how they change). Dead code, harmless to runtime, but worth deleting — an ESLint `no-unused-vars` rule would flag it.

## 5. `Home.jsx` — `React.memo`, and a Prop That's Never Actually Passed

```jsx
import React from "react";

const Home = ({ users }) => {
  console.log("home rendering...");
  return (
    <div>
      <h1>Home this side</h1>
    </div>
  );
};

export default React.memo(Home);
```

### 5.1 Bug Worth Calling Out Explicitly: Prop Name Mismatch With `App.jsx`

```jsx
// App.jsx
<Home greet={greet} />
```

```jsx
// Home.jsx
const Home = ({ users }) => { ... }
```

- `Home` destructures a prop called **`users`**, but `App.jsx` never passes a `users` prop to `Home` at all — it passes `greet` instead (the exact same prop `About` receives). As written, `users` inside `Home` is **always `undefined`**, and `Home` never renders anything using it anyway (there's no `{users.name}` or similar in its JSX), so this bug is currently invisible — nothing crashes, nothing looks wrong on screen. But it means this component isn't actually demonstrating what its own prop signature suggests it should be: a memoized child that receives the `users` object and would need to re-render whenever that object's *contents* the component cares about change.
- **Why this specifically undermines the point of the demo:** right now, both `Home` and `About` receive the exact same prop (`greet`), which is deliberately kept stable via `useCallback` — so neither one has anything in this file set that would ever force a re-render when `users` actually changes. A more complete demonstration would pass `users` to `Home` as intended, letting you observe the *other* half of the `React.memo` story: a memoized child that **does** re-render, correctly, when a prop it actually cares about changes (i.e., after clicking "Change name" and `users` becoming a new object reference) — as opposed to `About`, which never has a reason to re-render at all in this setup, since `greet` never changes.
- `greet` itself is received as a prop by `Home` but never called or used anywhere in the component body — unlike `About`, which (problematically, per §4.2) calls it directly. So for `Home`, receiving `greet` is functionally inert either way; the mismatch is really only a documentation/intent problem (the destructured prop name lies about what the component is meant to receive), not a currently-visible runtime bug.

### 5.2 What `React.memo` Is Actually Doing Here, Given the Bug

- Since `Home`'s only prop is (mistakenly) `greet`, and `greet` is stable across every render via `useCallback`, `Home` behaves identically to `About` in terms of when it re-renders: only on mount, never again for the lifetime of this component tree, regardless of which button is clicked. `React.memo` is "working" here in the narrow sense that no unnecessary re-renders happen — but it's not actually being *exercised* the way the file's own prop name (`users`) implies it's meant to be.

## 7. Consolidated Issues & Gotchas Checklist

| File | Issue | Severity | Fix |
|---|---|---|---|
| `Home.jsx` / `App.jsx` | `Home` destructures a `users` prop, but `App` passes `greet` instead — `users` is always `undefined` inside `Home` | Medium (currently invisible since `users` is unused in JSX, but undermines what the demo is meant to show) | Pass `<Home users={users} />` from `App`, and have `Home` actually render something derived from it, to demonstrate a memoized child that *does* need to re-render on a relevant prop change |
| `About.jsx` | `greet()` is called directly in the component's render body, not inside a click handler or `useEffect` | Medium (harmless with a `console.log`; a real anti-pattern once the called function has any actual side effect) | Wrap in `useEffect(() => { greet(); }, [greet])` if it's meant to run on mount/update, or move the call into an event handler if it's meant to run on user action |
| `About.jsx` | `let a = 10;` declared at module scope, never used | Low (dead code / lint warning) | Delete |
| `App.jsx` | `<h2>NAme is {users.name}</h2>` — typo in the literal JSX text (`NAme`) | Low (cosmetic, user-facing text) | `Name` |

> None of these break the demo's core lesson — `React.memo` + `useCallback` genuinely do prevent `Home`/`About` from re-rendering on every `count` increment, which is the headline point. The prop-name mismatch just means the *second* half of the lesson (a memoized component correctly re-rendering when a prop it legitimately depends on changes) isn't actually being demonstrated by this file set as it currently stands.

## Quick Summary

```
THREE TOOLS, ONE PROBLEM
- useMemo(fn, deps)     → caches a VALUE, recomputes only when deps change.
- useCallback(fn, deps) → caches a FUNCTION'S IDENTITY, same recompute rule.
- React.memo(Component) → skips a component's OWN re-render if its props
                           are shallow-equal to last render.
- None of the three does anything alone: React.memo needs stable props to
  compare against, which is exactly what useMemo/useCallback produce.

THIS MODULE'S SETUP (App.jsx)
- Two UNRELATED pieces of state: count (Increment) and users (Change name).
- calculation = useMemo(expensiveLoop, [users])
  → the 100-million-iteration loop only re-runs when `users` changes,
    NOT on every Increment click. Still fully synchronous/blocking when
    it DOES run — useMemo controls frequency, not blocking behavior.
- greet = useCallback(fn, [])
  → same function reference forever, which is what lets React.memo on
    Home/About actually detect "nothing changed" and skip re-rendering.

WHAT HAPPENS ON EACH CLICK
- Increment  → count changes, users doesn't → calculation NOT recomputed,
               greet reference unchanged → Home/About skip re-rendering.
- Change name→ users changes (new object) → calculation IS recomputed
               (loop reruns) → greet reference still unchanged →
               Home/About STILL skip re-rendering (see gotcha below).
- App itself ALWAYS re-renders on either click — memoization never
  protects a component from ITS OWN state changes, only its children
  from an unrelated parent re-render.

CONTRAST WITH MODULE 1's DERIVED STATE
- cartItem/subtotal (Module 1): cheap → recompute FRESH every render,
  no caching, simplest and safest.
- calculation (this module): expensive → cache via useMemo, only
  recompute when the specific dependency actually changes.
- Same underlying question both times ("should I store this or derive
  it fresh?"), opposite answers because the COST of deriving differs.

THE PROP-NAME BUG (App.jsx → Home.jsx)
- App passes <Home greet={greet} /> but Home.jsx destructures { users }.
  users is always undefined inside Home — currently invisible since
  Home never renders it, but means this file set never actually shows
  a memoized child re-rendering because a prop IT CARES ABOUT changed.

RENDER-BODY SIDE EFFECT (About.jsx)
- greet() is called directly inside the component function, not in a
  useEffect or event handler — a real anti-pattern (harmless here only
  because greet just logs a string).
```
