# React Router — Routing, Dynamic Params & Protected Routes

This module covers client-side routing using **React Router (v7)** — multi-page navigation without full browser reloads, dynamic URL parameters, and a common access-control pattern: protecting a route behind a condition.

---

## 1. A Notable Detail — `import ... from "react-router"`

```js
import { BrowserRouter } from "react-router";
import { Route, Routes } from "react-router";
import { NavLink } from "react-router";
import { useParams } from "react-router";
import { useNavigate } from "react-router";
import { Navigate } from "react-router";
```

Every import across this app comes from **`"react-router"`**, not the more commonly seen `"react-router-dom"`. This is intentional and version-specific, worth understanding:

- <cite index="59-1">In React Router v7, react-router-dom is a re-export of react-router, ensuring compatibility for existing projects while allowing new projects to use react-router directly.</cite>
- Historically (`v6` and earlier), `react-router` was the core routing engine (framework-agnostic), and `react-router-dom` added the browser-specific pieces (`BrowserRouter`, `Link`, `NavLink`, etc.) on top of it. <cite index="59-1">react-router-dom extends react-router with web-specific components like BrowserRouter, Link, and NavLink.</cite>
- **As of v7**, the two packages were consolidated — `react-router` itself now includes everything needed for web apps directly, and `react-router-dom` is kept around only as a compatibility re-export for older code. This app uses the newer, consolidated `"react-router"` import path throughout, which is the modern, recommended way to import in current projects.

## 2. Setting Up Routing — `main.jsx`

```jsx
import { createRoot } from "react-dom/client";
import "./index.css";
import App from "./App.jsx";
import { BrowserRouter } from "react-router";
import { ContextProvider } from "./context/MyContext.jsx";

createRoot(document.getElementById("root")).render(
  <BrowserRouter>
    <ContextProvider>
      <App />
    </ContextProvider>
  </BrowserRouter>
);
```

### `BrowserRouter` — The Foundation

<cite index="61-1">BrowserRouter is the component that connects your React app to the browser's native History API. It wraps your entire app (or the section that needs routing) and enables components inside it to read and respond to URL changes. Without it, hooks like useNavigate and useLocation will throw an error.</cite>

- It uses the browser's built-in **History API** (`pushState`, `replaceState`, the `popstate` event) to keep the URL bar in sync with what's rendered — <cite index="70-1">it keeps your UI in sync with the URL</cite> — without triggering a full page reload/refresh the way a normal `<a href="...">` link would.
- **Placement matters:** `BrowserRouter` wraps *everything* here — including `ContextProvider` — meaning both routing state and your app's shared context are available throughout the entire component tree. If `BrowserRouter` were placed *inside* `ContextProvider` instead, context would still work fine, but the ordering here (Router outermost) is the more conventional structure, since routing is typically the outermost layer of an app's architecture.

## 3. Defining Routes — `AppRoutes.jsx`

```jsx
import React from "react";
import About from "../pages/About";
import Products from "../pages/Products";
import { Route, Routes } from "react-router";
import Home from "../pages/Home";
import ProductDetail from "../pages/ProductDetail";
import ProtectedRoute from "./ProtectedRoute";

const AppRoutes = () => {
  return (
    <div className="h-screen">
      <Routes>
        <Route path="/" element={<Home />} />
        <Route
          path="/about"
          element={
            <ProtectedRoute>
              <About />
            </ProtectedRoute>
          }
        />
        <Route path="/products" element={<Products />} />
        <Route path="/detail/:id" element={<ProductDetail />} />
      </Routes>
    </div>
  );
};

export default AppRoutes;
```

### `Routes` vs `Route`

<cite index="61-1">Route and Routes: Define which component to render for a given path.</cite> Specifically:
- **`<Routes>`** is a **container** — it looks at the current URL and renders **whichever single `<Route>` matches**, out of all the `<Route>`s nested inside it.
- **`<Route path="..." element={<Component />} />`** — each individual mapping between a URL path and the component that should render there.

### The `path`/`element` Pattern

- `path="/"` → renders `<Home />` at the root URL.
- `path="/products"` → renders `<Products />`.
- `path="/about"` → renders `<About />`, but **wrapped** in `<ProtectedRoute>` (Section 4) — this is what makes it a *guarded* route rather than a plain one.
- `path="/detail/:id"` → a **dynamic route** (Section 5) — the `:id` segment is a placeholder that matches *any* value in that position of the URL (e.g. `/detail/1`, `/detail/42`, etc.), all routed to the same `ProductDetail` component.

### Why Routing Lives in Its Own File/Folder

- `AppRoutes.jsx` lives under a `routes/` folder, separate from `pages/` (which holds `Home`, `About`, `Products`, `ProductDetail`) and `components/` (which holds `Navbar`, `ProductCard`). This is a common, deliberate project-structure convention: **pages** are full route-level views, **components** are reusable pieces used *within* pages, and **routes** is where the URL-to-page mapping is centrally defined — keeping `App.jsx` itself clean (see Section 7).

## 4. `ProtectedRoute.jsx` — Guarding a Route

```jsx
import React from "react";
import { Navigate } from "react-router";

const ProtectedRoute = ({ children }) => {
  let isAdmin = false;

  if (!isAdmin) {
    console.log("hey i m running...");
    alert("you are not an admin");
    return <Navigate to={"/"} />;
  }

  return children;
};

export default ProtectedRoute;
```

### The Wrapper-Component Pattern (Again)

This is the exact same `children`-based **wrapper component** pattern from your earlier Context API notes — `ProtectedRoute` doesn't know or care *what* it's guarding; it just receives whatever JSX is nested inside it (here, `<About />`) as `children`, and decides whether to actually render it.

### The Guard Logic

```js
let isAdmin = false;

if (!isAdmin) {
  // block access
  return <Navigate to={"/"} />;
}

return children;   // allow access
```

- `isAdmin` is currently **hardcoded to `false`** directly inside the component — meaning **every single visit to `/about`** will be blocked, unconditionally, for every user, every time. This is clearly a placeholder/demo value; a real implementation would derive `isAdmin` from actual authentication state (e.g. pulled from context, or a login-check API call), not a hardcoded literal.
- **`<Navigate to={"/"} />`** — <cite index="63-1">rather than imperatively calling a navigate function, Navigate is a declarative React component: rendering it causes React Router to redirect immediately to the given path.</cite> Here, returning `<Navigate to="/" />` instead of `children` means React renders this redirect component instead of `About`, which causes an immediate redirect back to the home page (`/`).
- **Side effects before the redirect:** `console.log(...)` and `alert(...)` both run every time someone is blocked — useful for demonstrating that the guard logic actually executed, though a real app would likely replace the `alert()` with a proper in-app toast/notification, since browser `alert()` dialogs are blocking and generally considered poor UX for production apps.

### Where the Wrapping Happens

```jsx
<Route
  path="/about"
  element={
    <ProtectedRoute>
      <About />
    </ProtectedRoute>
  }
/>
```

- Only the `/about` route is wrapped this way — `/`, `/products`, and `/detail/:id` are all left completely open, with no guard at all. This demonstrates that route protection in React Router isn't a global on/off setting — it's applied **selectively, per route**, exactly where you nest a guard component around a given route's `element`.

## 5. Dynamic Routes — `:id` and `useParams`

### Declaring a Dynamic Segment

```jsx
<Route path="/detail/:id" element={<ProductDetail />} />
```

- The colon (`:id`) marks `id` as a **URL parameter** — a variable segment of the path. `/detail/1`, `/detail/17`, `/detail/anything` all match this single route definition, with whatever comes after `/detail/` captured as the value of `id`.

### Reading the Parameter — `useParams`

```jsx
// ProductDetail.jsx
import { useParams } from "react-router";

const ProductDetail = () => {
  let { id } = useParams();
  // ...
};
```

- <cite index="67-1">useParams lets you read the dynamic parameters from the current URL that were matched by the Route.</cite>
- `useParams()` returns an **object** whose keys match the `:param` names declared in the route — since the route was defined as `/detail/:id`, `useParams()` returns `{ id: "..." }`, immediately destructured to just `id`.
- **Important:** URL params are always **strings**, even if they represent a number (e.g. visiting `/detail/5` gives `id = "5"`, not `id = 5`). This matters if you ever need to do numeric comparisons or math with the id — you'd need to explicitly convert it (`Number(id)` or `parseInt(id)`).

### Using the Param to Fetch Specific Data

```jsx
let getSingleProductData = async () => {
  try {
    let res = await axios.get(`https://fakestoreapi.com/products/${id}`);
    setSingleProductData(res.data);
  } catch (error) {
    console.log("Detail api error", error);
  }
};

useEffect(() => {
  getSingleProductData();
}, []);
```

- The captured `id` is interpolated directly into the API URL via a template literal, fetching **that specific product's** details from the API, rather than the full product list.
- `useEffect(..., [])` — empty dependency array, so this fetch runs once on mount. **Worth flagging:** since `id` isn't listed as a dependency, if the user somehow navigated from `/detail/1` directly to `/detail/2` (e.g. via a "related products" link, without the component fully unmounting/remounting), this effect would **not** re-run, and the page would keep showing product 1's data. The safer version would be `useEffect(() => { getSingleProductData(); }, [id])`, so the fetch re-runs whenever the URL's `id` actually changes. In this specific app, this bug may not surface in practice (there's no in-page way to jump between two detail pages without going back through the product grid, which *does* fully remount `ProductDetail`), but it's a common gotcha worth knowing about dynamic routes in general.

### Rendering With Optional Chaining

```jsx
<span className="ml-1 font-semibold">
  {singleProductData.rating?.rate}
</span>
<span className="text-gray-500">
  ({singleProductData.rating?.count} Reviews)
</span>
```

- `singleProductData` starts as `{}` (empty object) via `useState({})`, **before** the API response has arrived.
- `singleProductData.rating` would be `undefined` at that point — so `singleProductData.rating.rate` would throw a runtime error ("Cannot read properties of undefined"). The **optional chaining operator (`?.`)** short-circuits safely instead: `singleProductData.rating?.rate` evaluates to `undefined` (rendering nothing) rather than crashing, if `rating` doesn't exist yet. Once the API response lands and `singleProductData` updates, `rating` exists and the chain resolves normally.
- Note other fields on the page (`singleProductData.title`, `.image`, `.price`, `.description`, `.category`) **don't** use `?.` — they're top-level fields, so reading them before the fetch resolves just renders `undefined` (shows nothing) rather than crashing, since you're not trying to access a *nested* property of something that doesn't exist yet. `rating` is the only field here that's itself an object with sub-properties, which is exactly why it's the one place optional chaining was necessary.

## 6. Client-Side Navigation — Two Approaches

This app demonstrates both of React Router's two ways to navigate: **declarative** (`NavLink`) and **imperative** (`useNavigate`).

### 6.1 `NavLink` — Declarative, for Persistent Nav Menus

```jsx
// Navbar.jsx
import { NavLink } from "react-router";

<NavLink to={"/"}>Home</NavLink>
<NavLink to={"/about"}>About</NavLink>
<NavLink to={"/products"}>products</NavLink>
```

- <cite index="61-1">Both Link and NavLink render an anchor tag that navigates without a full page reload. The difference is that NavLink automatically applies an active CSS class (or a class you define) to the link when its route is currently active — making it ideal for navigation menus where you want to visually highlight the current page.</cite>
- Functionally, clicking a `NavLink` updates the URL and swaps the rendered `<Route>`, without the browser doing a full page reload — the entire point of client-side routing (fast, app-like navigation instead of a full server round-trip per click).
- **Note:** this `Navbar` doesn't currently use `NavLink`'s active-styling feature (no custom `className` function passed to react to the active state) — it's used here purely for its navigation behavior, though the "active link highlighting" capability is available if styling were added later.

### 6.2 `useNavigate` — Imperative, for Programmatic Navigation

```jsx
// ProductCard.jsx
import { useNavigate } from "react-router";

const ProductCard = ({ product }) => {
  let navigate = useNavigate();

  return (
    <div
      onClick={() => navigate(`/detail/${product.id}`)}
      ...
    >
```

- <cite index="63-1">useNavigate is a hook for imperative navigation, useful when you need to navigate programmatically</cite> — rather than the user clicking directly on a link-like element, `useNavigate()` gives you a `navigate(...)` **function** you can call from inside any event handler or logic.
- Here, clicking anywhere on the product image `<div>` calls `navigate(`/detail/${product.id}`)`, dynamically building the correct detail-page URL for **that specific product** and redirecting there.
- **Why `useNavigate` instead of `NavLink` here?** The click target isn't a simple "always goes to the same fixed URL" link (like `Navbar`'s items) — it's a `<div>` wrapping a product image, where the destination URL depends on *which* product was clicked. `useNavigate` fits this dynamic, data-dependent navigation case better than a static `NavLink to="..."` would.

### Comparing the Three Navigation Mechanisms Used in This App

| Mechanism | Used In | Type | Best for |
|---|---|---|---|
| `<NavLink to="...">` | `Navbar.jsx` | Declarative | Fixed, always-visible nav menu items |
| `navigate(...)` (from `useNavigate()`) | `ProductCard.jsx` | Imperative | Navigation triggered by a non-link element, or where the destination is computed dynamically |
| `<Navigate to="...">` | `ProtectedRoute.jsx` | Declarative (but conditional) | Redirecting *automatically*, as a side effect of a component's render logic (e.g. access denied) |

## 7. Tying It Together — `App.jsx`

```jsx
import React from "react";
import Navbar from "./components/Navbar";
import AppRoutes from "./routes/AppRoutes";

const App = () => {
  return (
    <div className="flex flex-col gap-4">
      <Navbar />
      <AppRoutes />
    </div>
  );
};

export default App;
```

- `App` itself stays extremely thin: render the `Navbar` (always visible, regardless of route) above `AppRoutes` (which swaps out its content based on the current URL). This is the standard shape of a routed app's root component — a persistent layout shell (`Navbar`, and often a footer) wrapping whichever page is currently active.

## 8. Shared Context — `MyContext.jsx` & `Home.jsx`

```jsx
// MyContext.jsx
export const MyStore = createContext();

export const ContextProvider = ({ children }) => {
  const [productsData, setProductsData] = useState([]);
  return (
    <MyStore.Provider value={{ productsData, setProductsData }}>
      {children}
    </MyStore.Provider>
  );
};
```

```jsx
// Home.jsx
const Home = () => {
  let { productsData, setProductsData } = useContext(MyStore);

  let getProductsData = async () => {
    try {
      let res = await axios.get("https://fakestoreapi.com/products");
      setProductsData(res.data);
    } catch (error) {
      console.log("error in api", error);
    }
  };

  useEffect(() => {
    getProductsData();
  }, []);

  return (
    <div className="p-2 grid grid-cols-4 gap-4">
      {productsData.map((val) => (
        <ProductCard key={val.id} product={val} />
      ))}
    </div>
  );
};
```

- This follows the same shared-context pattern from your earlier Context API notes: `productsData` lives in context so it's *technically* reachable from anywhere in the app, though in this specific app only `Home` currently reads/writes it.
- `Home` fetches the **full product list** once on mount (`useEffect(..., [])`) and renders it as a grid of `ProductCard`s — this is the "browse all products" page, distinct from `ProductDetail`, which fetches and shows **one specific** product based on the URL's `:id`.
- **Worth noting:** `productsData` (the full list, used by `Home`) and `singleProductData` (one product, used by `ProductDetail`) are two **entirely separate** pieces of state, fetched via two **separate** API calls, even though they're hitting closely related endpoints (`/products` vs `/products/:id`). There's no caching or sharing between them — clicking into a product's detail page always triggers a fresh fetch for that one product, even if its data already exists inside `productsData` from the grid fetch moments earlier. This is a reasonable simplification for a learning project; a production app might avoid the redundant fetch by looking up the clicked product from the already-loaded `productsData` first.

## 9. Full Navigation Flow, End to End

```
User visits "/"
   → Routes matches path="/" → renders <Home/>
   → Home's useEffect fetches full product list → grid of ProductCards

User clicks a ProductCard's image
   → navigate(`/detail/${product.id}`) called
   → URL changes to e.g. "/detail/3", NO full page reload
   → Routes now matches path="/detail/:id" → renders <ProductDetail/>
   → useParams() reads { id: "3" }
   → ProductDetail's useEffect fetches THAT product specifically

User clicks "About" in Navbar
   → NavLink navigates to "/about"
   → Routes matches path="/about" → element is <ProtectedRoute><About/></ProtectedRoute>
   → ProtectedRoute renders first, checks isAdmin (hardcoded false)
   → isAdmin is false → alert shown, console logged
   → returns <Navigate to="/"/> INSTEAD of <About/>
   → user is redirected back to Home, never actually sees <About/>
```

## Quick Summary

```
BrowserRouter    → wraps the app, syncs UI with the browser's URL (History API)
Routes            → container that picks ONE matching Route to render
Route path/element → maps a URL path to a component

Dynamic routes:
  <Route path="/detail/:id" element={<ProductDetail/>} />
  useParams() → { id: "..." }   (always a STRING, even for numeric-looking ids)

Navigation, three ways:
  <NavLink to="...">      → declarative, for fixed nav menu links (supports active styling)
  useNavigate() → navigate(url)  → imperative, for dynamic/computed or non-link-triggered navigation
  <Navigate to="..."/>     → declarative REDIRECT, rendered conditionally (e.g. access control)

Protected routes = a children-wrapper component + conditional <Navigate/>:
  <ProtectedRoute><SomePage/></ProtectedRoute>
  → if condition fails: render <Navigate to="fallback"/> INSTEAD of children
  → if condition passes: render children normally

Gotchas flagged in this code:
  - isAdmin is hardcoded false → /about is unconditionally blocked for everyone right now
  - ProductDetail's useEffect has [] as deps, not [id] → wouldn't refetch if id changed
    without a full component remount
  - optional chaining (?.) needed only for nested fields (rating.rate) read before
    the API response has arrived, since the initial state is {}
```
