# Debouncing vs. Throttling — `App.jsx`

This module has one of each: a **debounced search** (waits for the user to *stop* typing before doing anything) and a **throttled scroll listener** (does something immediately, then refuses to do it again for a fixed window, no matter how much the user keeps scrolling). They look similar — both use `setTimeout` and both are "rate-limiting" *something* — but they solve opposite problems and are built with opposite mechanics. That contrast is the whole point of this file.

---

## 1. The Core Distinction

| | Debounce (search) | Throttle (scroll) |
|---|---|---|
| Question it answers | "Has the user *stopped*?" | "How long since I last *did* this?" |
| When does the action fire | Only **after** a pause of N ms with no new trigger | **Immediately** on the first trigger, then blocked for N ms |
| What a burst of events does | Keeps **resetting** the timer — action may never fire if triggers keep coming faster than N ms apart | Fires **once** at the start of the burst, ignores everything else until the cooldown ends |
| Built with | `setTimeout` + `clearTimeout` in a `useEffect` cleanup, keyed to the *changing* dependency (`searchData`) | A **persistent boolean flag** in a closure + `setTimeout` to flip it back, inside an effect that runs **once** |
| Where the delay lives | Re-created every time `searchData` changes | Created **once** when the scroll listener is attached |

> The mental shortcut: debounce = "wait for quiet." Throttle = "at most once every N."

## 2. Debouncing the Search — `useEffect` #1

```js
useEffect(() => {
  if (!searchData) {
    setProductsData(allProducts);
    return;
  }
  let timeout = setTimeout(() => {
    filteredData();
  }, 700);
  return () => clearTimeout(timeout);
}, [searchData]);
```

### 2.1 Why this re-runs on every keystroke

`[searchData]` is the dependency array, so **every single keystroke** re-runs this effect from scratch. That re-run is the entire mechanism — there's no explicit "cancel the old debounce" call visible in the code that isn't just React doing what effects always do:

1. User types a character → `searchData` changes → component re-renders.
2. React sees the effect's dependency changed, so before running the new effect body it first runs the **cleanup function from the previous run**: `clearTimeout(timeout)`. This kills whatever 700ms timer was already ticking from the last keystroke.
3. *Then* the new effect body runs and schedules a brand-new `setTimeout(..., 700)`.

So "debouncing" here isn't one special API — it's just the ordinary React effect cleanup lifecycle, exploited on purpose: **as long as keystrokes arrive faster than 700ms apart, no timer ever survives long enough to fire.** Only once the user pauses for a full 700ms does a scheduled `filteredData()` call finally survive to completion.

### 2.2 Tracing a fast typing burst

Typing `"shirt"` at normal speed (each letter well under 700ms apart):

```
type 's'  → schedule timer A (700ms)
type 'h'  → cancel A, schedule timer B
type 'i'  → cancel B, schedule timer C
type 'r'  → cancel C, schedule timer D
type 't'  → cancel D, schedule timer E
...700ms of silence...
timer E fires → filteredData() runs ONCE, filtering for "shirt"
```

`filteredData()` runs **exactly once** for the whole word, not once per letter. This is the actual point of debouncing a search box: it avoids re-filtering (and in a real app, re-querying an API) on every keystroke, and only does the expensive work once the user has settled on what they're actually searching for.

### 2.3 The empty-string special case — this is *not* debounced

```js
if (!searchData) {
  setProductsData(allProducts);
  return;
}
```

This branch runs **before** any timer is set, and it `return`s early — so clearing the search box (backspacing to `""`) resets `productsData` **instantly**, with zero delay. Only a *non-empty* query goes through the 700ms wait. This is a deliberate UX choice: there's no reason to make the user wait 700ms just to see the full list come back after clearing their search.

### 2.4 The stale-closure risk hiding in the dependency array

`filteredData` (defined outside this effect, at the top of the component) reads `allProducts` from its own closure:

```js
let filteredData = () => {
  let result = allProducts.filter((val) => ...);
  setProductsData(result);
};
```

But the debounce effect's dependency array is `[searchData]` **only** — `allProducts` is missing. That means: this effect does not know or care whether `allProducts` has changed; it only re-arms the timer when `searchData` changes. In this file that's harmless, because `allProducts` is set exactly once (on the initial fetch) and never reassigned afterward. But it's a real trap for anyone extending this component: if a "refresh product list" feature were added, a debounce timer already in flight would fire and filter against **whatever `allProducts` was at the time that render happened** — potentially the pre-refresh list — silently producing stale results. Fixing it would mean either adding `allProducts` to the dependency array, or inlining the filter logic directly into the effect so its real inputs are explicit.

## 3. Throttling the Scroll — `useEffect` #2

```js
useEffect(() => {
  let throttle = false;
  let handleScroll = () => {
    if (throttle) return;
    throttle = true;
    setScrollY(window.scrollY);
    setTimeout(() => {
      throttle = false;
    }, 2000);
  };
  window.addEventListener("scroll", handleScroll);
  return () => window.removeEventListener("scroll", handleScroll);
}, []);
```

### 3.1 Why the empty dependency array matters here

`[]` means this effect runs **once**, when `App` first mounts, and never again for the component's lifetime (until unmount). That single run is what makes the whole throttle mechanism work: `throttle`, `handleScroll`, and the event listener are all created **one time** and then just... sit there, listening.

### 3.2 `throttle` is a plain closure variable — and that's correct, not a bug

```js
let throttle = false;
```

This is **not** `useState` or `useRef`. At first glance that looks wrong — "shouldn't mutable state live in a ref?" — but it's actually the right call here specifically *because* the effect only runs once:

- `handleScroll` is defined **inside** the effect body, so it closes over that one `throttle` variable for as long as the listener is attached.
- Every scroll event calls the *same* `handleScroll` function, reading and writing the *same* `throttle` variable in its enclosing scope — exactly the persistence a `useRef` would give you, just via a normal JS closure instead of a React hook.
- If `useState` had been used instead, flipping `throttle` would trigger a re-render on every lock/unlock (twice per throttle window) for a value the UI never actually displays — pure wasted work. If the effect instead had a non-empty dependency array and re-ran on every render, a **new** `throttle = false` would be created each time, breaking the lock entirely. Neither of those is what's happening here — the `[]` array + closure combo is deliberate and correct.

### 3.3 Leading-edge behavior, traced through a continuous scroll

```
t=0.0s   scroll event → throttle is false → LOCK. setScrollY(current). schedule unlock at t=2.0s
t=0.3s   scroll event → throttle is true → IGNORED
t=0.9s   scroll event → throttle is true → IGNORED
t=1.7s   scroll event → throttle is true → IGNORED
t=2.0s   unlock timer fires → throttle = false
t=2.4s   scroll event → throttle is false → LOCK again. setScrollY(current). schedule unlock at t=4.4s
```

This is a **leading-edge** throttle: the *first* event in a burst fires immediately, and everything else in the next 2 seconds is dropped outright — not queued, not merged, just ignored. The practical consequence, visible in the UI (`scroll {scrollY}px` in the header), is that `scrollY` can sit **stale** for up to 2 full seconds while the user keeps scrolling, then suddenly jump to wherever they've scrolled *to* the next time the lock opens. A **trailing-edge** throttle (or throttle+trailing-call hybrid) would instead capture the *last* known scroll position right as the cooldown expires, giving a smoother "every 2s, tell me where I actually ended up" behavior — that's a valid alternative design, just not the one implemented here.

### 3.4 Why this doesn't need `clearTimeout` cleanup the way the debounce does

Notice the throttle's `setTimeout` (the one that flips `throttle` back to `false`) is never explicitly cancelled — only the scroll **event listener** is removed in the effect's cleanup:

```js
return () => window.removeEventListener("scroll", handleScroll);
```

This is fine: if `App` unmounts while a throttle-unlock timer is still pending, the timer will still fire 2 seconds later and set `throttle = false` on a closure that's no longer reachable from anywhere — it just becomes garbage with no effect on anything, since `handleScroll` (the only thing that reads `throttle`) can no longer be called once the listener is removed. Contrast with the debounce's `clearTimeout` in §2, which is load-bearing: if that cleanup were removed, a stale `filteredData()` call could still fire on unmount and call `setProductsData` on an unmounted component.

## 4. Side-by-Side: What Would Happen With the Patterns Swapped

It's worth imagining the mistake of using each pattern for the *other* trigger, to see why the pairing matters:

- **Throttling the search instead of debouncing it:** typing "shirt" would fire `filteredData()` on the very first keystroke (`"s"`), then again after the cooldown if the user was still typing, filtering against `"s"`, then partial words, then finally `"shirt"` — several wasted, visibly-wrong intermediate filter passes instead of one correct one at the end.
- **Debouncing the scroll instead of throttling it:** `scrollY` would only ever update once the user **completely stopped scrolling** for 700ms, meaning the header's live scroll indicator would show nothing at all *during* continuous scrolling and only catch up once motion fully stopped — arguably worse for a "live position" readout, where throttling's periodic-but-live updates are the better fit.

This is why search boxes are almost universally debounced (you want the *settled* query) and scroll/resize listeners are almost universally throttled (you want *periodic* updates without flooding the handler on every pixel of movement).

## Quick Summary

```
DEBOUNCE (search) — "wait for quiet"
- useEffect([searchData]) re-runs on every keystroke.
- Each re-run's CLEANUP clears the previous keystroke's timer
  (clearTimeout) before scheduling a new 700ms one.
- Only a keystroke followed by 700ms of silence lets a timer survive
  long enough to actually call filteredData().
- Empty string ("") bypasses the timer entirely — instant reset to
  the full list, no 700ms wait.
- Gotcha: effect deps = [searchData] only, NOT allProducts. Harmless
  today (allProducts set once on mount) but a stale-closure trap if a
  refetch feature is ever added.

THROTTLE (scroll) — "at most once every N"
- useEffect([]) runs ONCE — sets up one listener for the component's
  whole life.
- `throttle` is a plain closure variable (not useState/useRef) —
  correct specifically because the effect never re-runs, so the
  closure persists exactly like a ref would.
- LEADING-EDGE: fires instantly on the first scroll event, then
  ignores everything for 2000ms, then re-arms on the next event.
- Displayed scrollY can lag up to 2s behind the real position during
  continuous scrolling — a trailing-edge variant would instead capture
  the latest position right as the cooldown ends.
- No clearTimeout needed on unmount (only removeEventListener) because
  a stray unlock-timer firing after unmount touches a closure nothing
  can call into anymore — harmless, unlike the debounce's timer.

WHY THEY'RE BUILT DIFFERENTLY
- Debounce needs a delay that RESETS on every new trigger → lives in
  an effect keyed to the changing value, cancelled via cleanup.
- Throttle needs a lock that OUTLASTS individual triggers → lives in
  a persistent closure from a one-time effect, self-resetting via its
  own setTimeout rather than React's cleanup lifecycle.
```
