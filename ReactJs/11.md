# React — Context API

## 1. The Problem Context API Solves — Prop Drilling

Before getting into the API itself, it's worth being precise about **why** it exists.

> **DSM — "Data Sharing Manager"**: a way of thinking about Context API's job — it exists purely to share data across components without manually passing it through every layer in between.

### What is Prop Drilling?

In a normal React app, data only flows **one way**: parent → child, via props (as covered in the earlier state-lifting notes). If a deeply nested component needs a piece of data that lives several levels up, you'd normally have to pass it down as a prop through **every intermediate component**, even ones that don't actually use that data themselves — they just pass it along.

<cite index="37-1">State should be held by the highest parent component in the stack that requires access to the state. To illustrate, if you have many nested components, and the component at the top and bottom of the stack need access to the state, without Context you'd need to pass the state as props through each nested component in between — this is called "prop drilling."</cite>

```
App (has the data)
  └── Layer1 (doesn't need it, just passes it through)
        └── Layer2 (doesn't need it, just passes it through)
              └── Layer3 (doesn't need it, just passes it through)
                    └── DeepComponent (finally needs it)
```

This is exactly the problem the Context API was built to eliminate.

### Why It Was Needed

- Prop drilling makes components **tightly coupled** to data they don't even use — `Layer1`, `Layer2`, `Layer3` above all need a prop declared just to forward it, cluttering their signatures.
- It makes refactoring painful — renaming or restructuring a prop means touching every intermediate component in the chain.
- **Context API solves this directly**: <cite index="36-1">it lets a value be passed deep into the component tree without explicitly threading it through every component</cite> — any component, no matter how deeply nested, can reach up and read the value directly, skipping every layer in between.

## 2. Context API vs. Global State Management (GSM) Libraries

Your notes group these under two categories:

| Category | Tools | Scope |
|---|---|---|
| **Context API** | React's own built-in `createContext`/`useContext` | Best for simpler, less frequently-changing shared data (themes, auth user, locale, etc.) |
| **GSM (Global State Management)** | Redux, Zustand (third-party libraries) | Built for larger apps with complex, frequently-updating shared state, offering more tooling (devtools, middleware, selective re-rendering optimizations, etc.) |

Context API is part of React itself — no extra install needed — while Redux and Zustand are separate libraries you'd add on top of React specifically when an app's shared-state needs outgrow what Context comfortably handles (Context has known re-render characteristics that can become a performance concern at scale — every consumer of a context re-renders whenever that context's value changes, with no built-in fine-grained subscription like some GSM libraries offer).

## 3. Setting Up Context — `createContext`

```js
// context/MyContext.jsx
import { createContext } from "react";

export const MyStore = createContext();
```

- <cite index="32-1">Call createContext outside of any components to create a context.</cite>
- <cite index="32-1">The context object itself does not hold any information — it represents which context other components read or provide.</cite> Think of `MyStore` as a **channel** or **label**, not a container of data by itself.
- `createContext()` optionally accepts a **default value** as its argument (e.g. `createContext("light")`). <cite index="32-1">This defaultValue is the value the context has when there is no matching context provider in the tree above the component reading it</cite> — <cite index="38-1">it's only used when a component doesn't have a matching Provider above it, useful for testing components in isolation, and this default is static and never changes over time.</cite> In your code, `createContext()` is called with **no** default value.
- <cite index="32-1">It's common practice to declare context in its own separate file, then export it so other files can import it, the same way components are exported/imported.</cite> This is exactly the `context/MyContext.jsx` file structure your notes describe.

## 4. The Provider Component

```jsx
export const ContextProvider = ({ children }) => {
  return (
    <MyStore.Provider value={{span1: "C", h1: "omponent", span2: "4"}}>
      {children}
    </MyStore.Provider>
  );
}
```

### 4.1 What Is `.Provider`?

- Every context object created by `createContext()` comes with a `.Provider` component attached to it: <cite index="32-1">SomeContext lets you provide the context value to components.</cite>
- Wrapping a part of your component tree in `<MyStore.Provider>` makes the given `value` available to **every descendant** inside it — <cite index="36-1">any component can read it, no matter how deep it is</cite>.
- **Outside** the `<MyStore.Provider>` wrapper, components have no access to this context's value at all (they'd fall back to the `defaultValue` from `createContext()`, if one was set — otherwise `undefined`).

### 4.2 How `children` Works Here

```jsx
const ContextProvider = ({ children }) => { ... }
```

- `ContextProvider` is written as a **wrapper component** — it takes whatever JSX is nested *inside* it (via the special `children` prop, which React automatically populates whenever a component is used with an opening/closing tag pair) and simply places that content inside `<MyStore.Provider>`.
- This means `ContextProvider` doesn't need to know or care *what* it's wrapping — whatever gets passed as children (in this case, your entire `<App />` tree, per Section 6) is rendered right where `{children}` appears, now nested inside the actual context Provider.
- This is the exact same `children`-prop pattern used any time you build a reusable "wrapper" component (modals, layout shells, etc.) — nothing context-specific about `children` itself; what's context-specific is *what* it's being wrapped in.

### 4.3 The `value` Prop — Why It's a Single Object

```jsx
value={{span1: "C", h1: "omponent", span2: "4"}}
```

- <cite index="32-1">value is the value that you want to pass to all the components reading this context inside this provider, no matter how deep — the context value can be of any type.</cite>
- **Only one `value` prop is allowed per Provider** — there's no way to pass `value1={}` `value2={}` etc. So whenever you need to share **multiple** pieces of data through one context, the standard solution is to bundle them all into a **single object**, exactly as done here: `{ span1: "C", h1: "omponent", span2: "4" }` is one object carrying three separate values under one `value` prop.
- Note this is a plain **hardcoded/static** object here — not driven by `useState`. This context never changes after the app starts; if you wanted the context's value to be dynamically updatable (e.g. a theme toggle, a logged-in user that can change), you'd typically hold it in `useState` *inside* `ContextProvider` and pass both the current value **and** its setter function through the same `value` object — <cite index="35-1">the React Context API is stateless by default and doesn't provide a dedicated method to update the context value from consumer components, but this can be easily implemented by integrating useState() or useReducer(), and providing an update function right in the context next to the value itself.</cite>

## 5. `useContext` — Reading the Value

```jsx
let { span1, h1, span2 } = useContext(MyStore);
```

- <cite index="34-1">Call useContext at the top level of your component to read and subscribe to context.</cite>
- <cite index="34-1">useContext returns the context value for the calling component — it is determined as the value passed to the closest matching Provider above the calling component in the tree.</cite> <cite index="34-1">If there is no such provider, the returned value will be the defaultValue passed to createContext for that context.</cite>
- `useContext(MyStore)` returns the **entire object** you gave to `value={...}` — so it's destructured immediately (`{ span1, h1, span2 }`) to pull out the three individual pieces, the same object-destructuring pattern seen throughout your earlier notes.
- **Crucially, no matter how deeply nested a component is** (as demonstrated below — `Component4` is nested 4 levels deep), `useContext(MyStore)` reaches straight to the nearest enclosing `<MyStore.Provider>` and grabs its value — no intermediate component (`Component1`, `Component2`, `Component3`) needed to know or forward anything.
- <cite index="34-1">The returned value is always up-to-date — React automatically re-renders components that read a context if that context's value changes.</cite> (In this specific app, the value never changes after mount, so this behavior isn't visibly demonstrated here, but it's an important property of Context in general.)

## 6. Wiring It Up — `main.jsx`

```jsx
import { createRoot } from "react-dom/client";
import "./index.css";
import App from "./App.jsx";
import { ContextProvider } from "./context/MyContext.jsx";

createRoot(document.getElementById("root")).render(
  <ContextProvider>
    <App />
  </ContextProvider>
);
```

- This is the step that actually **activates** the context for the whole app: `<App />` (and therefore everything inside it) is passed as `children` into `<ContextProvider>`.
- Since `ContextProvider` wraps `<MyStore.Provider value={...}>` around whatever `children` it receives (per Section 4.2), the entire `App` component tree is now nested inside that Provider — meaning **every single component in the app**, at any depth, can call `useContext(MyStore)` and get the value.
- This top-level wrapping (at the very root of the render tree, above even `App` itself) is the standard placement for a context provider meant to be globally available — matching the general guidance that <cite index="37-1">a Context Provider should wrap the tree of components that need the state.</cite>

## 7. Full Code Walkthrough — The Nested Component Chain

This app demonstrates prop-free deep data sharing using a chain of 4 nested components.

```
App
 └── AllComponents
       └── Component1
             └── Component2
                   └── Component3
                         └── Component4   ← the only one that actually uses useContext
```

### 7.1 `App.jsx`

```jsx
import React from 'react'
import AllComponents from './AllComponents'

const App = () => {
  return (
    <div className='app'>
      <AllComponents />
    </div>
  )
}

export default App
```

Just a thin wrapper rendering `AllComponents` — no context logic here at all.

### 7.2 `AllComponents.jsx`

```jsx
import React from "react";
import Component1 from "./components/Component1";

const AllComponents = () => {
  return (
    <div className="all-components comp">
      <h1>All Components</h1>
      <div className="box box0">
        <Component1 />
      </div>
    </div>
  );
};

export default AllComponents;
```

Renders a heading label ("All Components") and nests `Component1` inside a styled `.box`. No props passed down, no context read here — purely structural.

### 7.3 `Component1.jsx` → `Component2.jsx` → `Component3.jsx`

```jsx
// Component1.jsx
const Component1 = () => {
  return (
    <div className="c1 comp">
      <h1>Component 1</h1>
      <div className="box box1">
        <Component2 />
      </div>
    </div>
  );
};
```

```jsx
// Component2.jsx
const Component2 = () => {
  return (
    <div className="c2 comp">
      <h1>Component 2</h1>
      <div className="box box2">
        <Component3 />
      </div>
    </div>
  );
};
```

```jsx
// Component3.jsx
const Component3 = () => {
  return (
    <div className="c3 comp">
      <h1>Component 3</h1>
      <div className="box box3">
        <Component4 />
      </div>
    </div>
  );
};
```

- Each of these three follows the **exact same pattern**: render a labeled box, nest the next component inside it.
- **None of them receive or forward any props** — this is the entire point being demonstrated. In a prop-drilling world, if `Component4` needed `span1`/`h1`/`span2` from a parent, `Component1`, `Component2`, and `Component3` would *all* need to accept and pass those values along as props, even though none of them actually use the data themselves. Context eliminates that entirely.

### 7.4 `Component4.jsx` — The Consumer

```jsx
import React, { useContext } from "react";
import { MyStore } from "../context/MyContext";

const Component4 = () => {
  let {span1, h1, span2} = useContext(MyStore);

  return (
    <div className="c4 comp">
      <div className="box box4">
        <span>{span1}</span>
        <h1 className="h1">{h1}</h1>
        <span>{span2}</span>
      </div>
    </div>
  );
};

export default Component4;
```

- `Component4` is nested **4 levels deep** (`App` → `AllComponents` → `Component1` → `Component2` → `Component3` → `Component4`), yet it reads `span1`, `h1`, `span2` **directly** from context — no prop was passed through any of the intermediate components.
- Rendered output: `<span>C</span><h1>omponent</h1><span>4</span>` — visually reading as **"C" + "omponent" + "4"** side-by-side, spelling out **"Component4"** across the three separate elements. This is a playful way of visually confirming that the context value genuinely made it all the way down to this specific component — the rendered text literally names which component successfully consumed the context.

## 8. Styling Notes (`index.css`)

- **CSS custom properties (`:root { --bg: ...; }`)** define a small design-token system — background/surface/border/text colors, plus accent colors (pink, coral, cyan, green) — reused throughout via `var(--name)`.
- **Nested "telescoping" box sizes** — `.all-components { height: 80%; width: 70%; }`, then `.c1 { 95%/90%; }`, `.c2, .c3 { 82%/82%; }`, `.c4 { 60%/50%; }` — each nested box is sized as a percentage *of its parent*, which is what visually produces the "boxes within boxes, shrinking inward" layout matching the component nesting structure.
- **`color-mix(in srgb, var(--pink) 55%, transparent)`** — a modern CSS function that blends a color with transparency directly in CSS (mixing 55% of the pink token with transparent), used to create softened, semi-transparent border colors per box (`.box1`, `.box2`, `.box3`) without needing separate `rgba()` values hardcoded for each accent color.
- **`.box4`** (the innermost, `Component4`'s box) gets distinct green-tinted styling (`--green-bg`, `--green-border`, glowing `box-shadow`) to visually set apart the component that actually consumes the context, versus the neutral gray styling (`box0`) through pink/coral/cyan (`box1`–`box3`) used for the purely structural pass-through components.
- All `.box` elements share hover states (`transform: translateY(-2px)`, deepened shadows) for a subtle "lift" interaction effect.

## Quick Summary

```
Problem: Prop Drilling
  - passing data through every intermediate component, even ones that don't use it

Solution: Context API
  createContext()                 → creates a "channel" (holds no data itself)
  <MyStore.Provider value={...}>  → makes a value available to ALL descendants, any depth
  useContext(MyStore)             → any nested component reads the value DIRECTLY,
                                     skipping every component in between

Rules:
  - A Provider only accepts ONE `value` prop → bundle multiple values into one object
  - Components outside the Provider fall back to createContext()'s default value (or undefined)
  - Context consumers re-render automatically whenever the Provider's value changes

Context API vs Redux/Zustand (GSM):
  - Context API: built into React, great for simpler/less-frequent shared data
  - Redux/Zustand: third-party, built for larger apps with complex/frequent state updates
```
